# PROMPTS — 派工提示登錄簿

把 93 個 atomic story 交給 Claude Code agent 執行的提示集合。

---

## 快速使用

```bash
python3 tools/prompt.py --ready              # 現在可以開工的 story
python3 tools/prompt.py --ready --done T01,T02,T04   # 標記已完成後重算
python3 tools/prompt.py B06                  # B06 的派工提示（直接貼給 agent）
python3 tools/prompt.py B06 --review         # B06 的審查提示（開新 session 用）
python3 tools/prompt.py --wave 0             # 整個波次的提示
```

派工與審查提示由 `dag.json` 自動填入前置、阻擋、檔案所有權、關鍵路徑標記，
所以**不需要手寫**。本文件收錄的是產生器做不到的那幾種。

## 六種提示，各自的時機

| # | 提示 | 什麼時候用 | 來源 |
|---|---|---|---|
| 1 | **開場**（角色） | 開一個新 agent session 的第一則訊息 | 本文件 §1 |
| 2 | **派工** | 指派一個 story | `prompt.py <ID>` |
| 3 | **審查** | story 回報完成後，**開新 session** 驗收 | `prompt.py <ID> --review` |
| 4 | **契約變更** | 有人動了 `CONTRACTS.md` | 本文件 §2 |
| 5 | **整合同步** | `E01` 首次真硬體整合 | 本文件 §3 |
| 6 | **卡關升級** | agent 卡住或想越界 | 本文件 §4 |

> **審查一定要開新 session。** 同一個 session 裡的 agent 剛寫完程式碼，
> 會傾向認為自己寫得對——它記得自己的意圖，而不是只看得到程式碼。
> 換一個沒有前情的 session 來讀驗收條件，才抓得到問題。

## §1 開場提示（角色）

開新 agent session 時貼這一則，之後再貼派工提示。**一個 session 只服務一條軌道**。

### W0 — 你自己（韌體 + 硬體實驗 + 契約決策）

W0 不是 agent，是你。你負責的是 agent 做不到的事：

- **A 軌 15 個 story** — 需要燒錄到實體板子、用手機相機看紅外光點、量電流
- **E 軌 8 個 story** — 需要你本人戴上裝置說話
- **T01–T03 契約決策** — 需要領域判斷做取捨（Slaney vs HTK、時間戳取樣點）

你可以請 agent 幫忙**寫** A 軌的程式碼，但驗收必須你來。

### W1 / W2 — Agent session 開場

```
你是這個專案的開發協作者，負責其中一條軌道。

## 專案

雙 VL53L7CX ToF 矩陣 + 骨傳導麥克風的無聲語音介面（SSI）研究專案。
硬體是 ESP32-S3（QT Py），韌體用 ESP-IDF，主機端是 Python + 原生 HTML/JS。
目標是驗證「ToF 矩陣能否讀出唇形」，並做一個 8 選項的閉集合辨識 Demo。

原始設計含 sEMG，但**本專案沒有 sEMG 感測器**，只有 ToF + 骨傳導麥克風。
特徵是 104 維（ToF 64 + Mel 40），不是簡報上的 105 維。

## 工作方式

- 93 個 atomic story，一個檔案一個，在 `stories/<軌道>/`。
- `CONTRACTS.md` 是跨軌介面的單一事實來源。**任何介面問題先查它。**
- 每條軌道有固定的檔案所有權（見 `CONTRACTS.md` §5），
  **同一時間有別的 agent 在改別的目錄**，越界就是衝突。
- 我會一次給你一個 story。做完回報，等我確認再給下一個。

## 三條規則

1. **一次只做一個 story。** 不要順手做下一個——它的其他前置可能還沒完成。
2. **契約有歧義就停下來問，不要自己決定。**
   兩個 agent 對同一個歧義做出不同決定，就是整合時爆炸的來源。
3. **不要重構相鄰的程式碼。** 看到問題就回報，不要動手。

## 禁止讀取

- `vl53l7cx_test/build/**` — 1589 個編譯產物
- `vl53l7cx_test/components/vl53l7cx_uld/include/vl53l7cx_buffers.h`
  — 22012 行的感測器韌體 blob，讀它沒有任何資訊價值
- `vl53l7cx_test/components/vl53l7cx_uld/**` — ST 官方驅動，唯讀

搜尋整個 repo 時一律排除：`--glob '!build/**' --glob '!**/vl53l7cx_buffers.h'`

先讀 `README.md` 和 `CONTRACTS.md`，然後告訴我你準備好了。不要開始寫任何程式碼。
```

**最後那句「不要開始寫任何程式碼」很重要。** 沒有它，agent 讀完 README 常常會直接
開始做它覺得最該做的事——通常是波 0 的某個 story，但不見得是你要它做的那個。

## §2 契約變更提示

`CONTRACTS.md` 改動時，**每個進行中的 agent session 都要收到這則**。

```
CONTRACTS.md 有變更，你手上的 story 可能受影響。

## 變更內容

章節：<例如 §1.3 t_us 取樣點>
原本：<舊規定，若原本沒規定就寫「未規定」>
現在：<新規定>
原因：<為什麼改>

## 你要做的

1. 重讀 CONTRACTS.md 的該章節
2. 檢查你已經寫的程式碼是否違反新規定
3. 回報下列其中之一：
   - 「不受影響」+ 一句話說明為什麼
   - 「需要修改」+ 具體哪些檔案哪些行 + 你打算怎麼改（**先別動手**）
   - 「這個變更會讓 <某條驗收條件> 無法達成」+ 說明

不要自己判斷「這個改動應該沒差」就繼續。介面的細微差異正是整合爆炸的來源。
```

### 契約變更的傳染範圍

| 改到什麼 | 要通知誰 |
|---|---|
| §1 協定 v2 | A 軌 + B 軌全部進行中的 session |
| §2 HDF5 schema | B 軌 + D 軌 |
| §3 特徵規格 | A11/A12/A14 + B14 + D01/D02/D03 |
| §4 HTTP/SSE | B 軌 + C 軌 |
| §6 詞彙集 | C15 + D08 |

## §3 整合同步提示（E01）

`E01` 是 A 軌與 B 軌第一次真接。**整合問題會在這一刻集中爆發**，
所以這則提示的重點是「先診斷，不要急著修」。

```
現在做 E01：協定 v2 韌體第一次接上真實的 bridge。

這是 A 軌與 B 軌的第一個整合點。兩邊都是照著 CONTRACTS.md 各自開發的，
所以問題會集中在**契約沒寫清楚的地方**，而不是程式碼寫錯。

## 先診斷，不要急著修

拿到真實的序列埠輸出後，逐項核對：

1. 每一種 $ 行的**欄位數量**對不對？（$T 應該有 **2 × dim** 個值——
   ⚠️ `dim` 是 zone 總數（16|64），**不是邊長**；邊長是 `$STATUS` 的 `res=`（4|8）。
   照 `dim²` 檢查會永遠對不上）
2. **欄位順序**對不對？（距離在前、signal rate 在後）
3. **單位**對不對？（signal 是否已經除以 100）
4. **無效值**的表示是否一致？（-1）
5. t_us 的**取樣點**是否符合契約？
   - ToF：check_data_ready 回 true 的當下
   - Mic：音框第一個 sample 的時間（不是讀取回傳時刻）
6. seq 是否每個資料流獨立遞增？

## 發現不一致時

先判斷**哪一邊錯了**：

- 契約寫得清楚，某一邊沒照做 → 那一邊改
- 契約沒寫或寫不清 → **停下來，先更新 CONTRACTS.md**，再改程式碼

第二種情況最常見，也最危險——如果你直接改程式碼讓兩邊對上，
契約仍然是模糊的，下一個 agent 還會再踩一次。

## 檢查清單（E01 的驗收條件）

- [ ] $STATUS 顯示 proto=2 且 fw sha 正確
- [ ] 4×4 實測幀率 ≥ 29 Hz（確認 A04 的修正生效）
- [ ] 掉幀率 < 1%，且韌體(A05)與主機端(B03)的數字一致
- [ ] 30 分鐘 heap 下降 < 2 KB
- [ ] 時鐘對齊殘差 p95 < 5 ms（B04）
- [ ] 拍手測試 10 次，音訊 peak 與 ToF 事件時間差 < 20 ms
- [ ] 錄下 5 分鐘原始 log 存進 logs/（供 T05 重播用）

回報時，把「契約需要補強的地方」單獨列一節。
```

## §4 卡關升級提示

agent 卡住、繞圈、或想越界時用這則。**不要直接說「你做錯了，重做」**
——那會讓它丟掉已經對的部分。

```
先停下來，不要再改程式碼。

回答這四個問題，用最短的篇幅：

1. 你現在卡在哪一個具體的技術問題？（一句話）
2. 你試過哪些方法？各自為什麼失敗？
3. 這個問題是出在：
   (a) CONTRACTS.md 沒規定或規定不清
   (b) story 的驗收條件本身有矛盾
   (c) 前置 story 其實沒做完
   (d) 純粹是實作難度
4. 如果我給你一個決定（例如「就用 X 方案」），你能繼續嗎？

回答完就停，等我回覆。不要在回答的同時繼續嘗試。
```

### 越界時

```
你剛才修改了 <路徑>，那不屬於你這條軌道（見 CONTRACTS.md §5）。

請把那個檔案還原成你修改前的狀態，然後告訴我：
- 為什麼你需要改它？
- 你想達成的效果是什麼？

如果那個改動確實必要，我會把它變成一個獨立的 story 交給對應的軌道，
或是更新 CONTRACTS.md。但不能由你直接改。
```

## §5 波 0：六個現成的派工提示

這六個零依賴，**現在就能開工**。指令產生完整提示：

```bash
python3 tools/prompt.py T01     # ⚡ 關鍵路徑
python3 tools/prompt.py T02
python3 tools/prompt.py T03
python3 tools/prompt.py T06
python3 tools/prompt.py A04     # 🔧 需硬體
python3 tools/prompt.py A10     # 🔧 需硬體
```

### 建議的開工順序

| 順序 | Story | 給誰 | 為什麼 |
|---|---|---|---|
| 1 | `T01` | **你** | 關鍵路徑起點，且需要領域判斷（時間戳取樣點） |
| 2 | `T04` | Agent | **解鎖 B/C/D 三軌共 136 h 的工作** |
| 3 | `T02` `T03` | Agent | 解鎖 D 軌 |
| 4 | `T06` | Agent | 建立檔案所有權，之後才能安全平行 |
| 5 | `A04` `A10` | **你** | 需要板子；A10 是 spike，3 h 上限 |

`T01` 建議你自己做，因為裡面有幾個決定 agent 沒有足夠脈絡判斷：

- **Mel 用 Slaney 還是 HTK 尺度** — librosa 預設 Slaney、多數 C 實作用 HTK。
  不一致的話 `A12` 的驗收條件「與 librosa 相關係數 > 0.95」永遠達不到
- **`$M` 的 `t_us` 是音框起點還是終點** — 差一整個音框 32 ms，
  而你要量的唇動先行只有 50–150 ms，方向搞錯會系統性偏移
- **8×8 模式下 780 bytes 的行長是否可接受**

## §6 反模式

以下這些提示看起來合理，實際上會製造問題。

### ❌ 「把 B 軌做完」

```
把 B 軌的 19 個 story 都實作出來。
```

**為什麼壞**：agent 會自己決定順序，而它看不到 A 軌與 C 軌的進度。
`B05` 需要 `A09` 已經燒錄、`B18` 需要 `A08`——它會卡住或自己造假的介面繞過。
而且 19 個 story 的 context 會超出單一 session 的有效範圍，後半段品質急降。

**正確**：一次一個，做完回報再給下一個。

### ❌ 「順便把測試也補一補」

```
實作 B06，順便把 B01 到 B05 缺的測試也補上。
```

**為什麼壞**：B01–B05 可能是別的 agent 寫的，或是還在進行中。
「補測試」會讀進大量不屬於這個 story 的程式碼，然後基於誤解寫出錯的測試。

**正確**：測試需求寫在各自 story 的驗收條件裡。缺了就開一個新 story。

### ❌ 「這個驗收條件先跳過，之後再說」

```
先不用管「掉幀率 < 1%」那條，先讓它跑起來。
```

**為什麼壞**：驗收條件是這個 story 存在的理由。跳過之後沒有人會記得回來補，
而 `E01` 整合時才發現掉幀 15%，那時要回溯的範圍已經很大了。

**正確**：如果條件真的達不到，讓 agent 明確回報「未通過 + 原因」，
你來決定是接受、改條件、還是開新 story。

### ❌ 讓寫的人自己審

```
（同一個 session）你剛寫完 B06，現在檢查一下有沒有問題。
```

**為什麼壞**：agent 記得自己的意圖，會用意圖去讀程式碼，而不是只看程式碼本身。
它會說「這裡是對的，因為我的想法是……」——但下一個讀這段程式碼的人沒有那個想法。

**正確**：`prompt.py <ID> --review` 開新 session。

## §7 給 agent 的 story 適配度

| 適合度 | Story | 理由 |
|---|---|---|
| ✅ **很適合** | D01–D08、D10–D20 | 純 Python 函式，輸入輸出明確，可寫 pytest 自我驗證 |
| ✅ **很適合** | B01、B03、B06、B07、B08、B14、B15 | 有 mock device 可端到端測試 |
| ✅ **很適合** | T04、T05 | 規格明確的工具程式 |
| 🟡 **可以但要盯** | C01–C05、C11–C14、C20–C24 | 能寫，但視覺類驗收條件要人工確認 |
| 🟡 **可以但要盯** | A 軌全部 | 能寫程式碼與編譯，**上機驗證必須你來** |
| ❌ **不要交** | C06、C09、C16、C25 | 需要視覺判斷「這樣看起來對不對」 |
| ❌ **不要交** | T01–T03 | 契約決策需要領域知識做取捨 |
| ❌ **不要交** | E 軌全部 | 需要你本人戴上裝置 |

**C06、C09、C16 這三個特別要注意**：它們的驗收條件是
「圓唇與展唇有肉眼可見的不同圖樣」「2 公尺外可讀」「動畫流暢不掉幀」——
agent 無法判斷這些，只能寫出「應該可以」的程式碼。

可以讓 agent 寫初版，但**驗收一定要你自己開瀏覽器看**。
