# B20 — bridge 讀取迴圈解耦（掉幀根因）

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E1 訊號地基 |
| **估時** | 2.0 h |
| **前置** | `B01`, `B03`, `B19` |
| **阻擋** | `E01`, `E05` |
| **需要硬體** | 否（用 mock 就能重現與驗證） |
| **可平行於** | C 軌、D 軌全部 |

## Story

**As a** 資料蒐集流程
**I want** bridge 在高頻寬下不要自己弄丟幀
**so that** `E05` 蒐集的主資料集不是在一個會漏資料的管線上錄出來的

## 為什麼會有這個 story

`B19` 實作品質指標時，**自己的警報在「沒注入任何故障」的測試裡響了**：

```
mic：主機算出 3 次掉幀，裝置只認 0 次。
差額為正代表幀在傳輸途中遺失（UART overrun 或 bridge 跟不上），不是計數誤差。
```

實測掉幀率 **0.7%–1%**，而當時：
- 跑在**本機 pty**（不是真實 UART，沒有電氣層問題）
- **只用了 18% 頻寬**

§1.4 的真機組態是 4×4+Mel **54%**、8×8+Mel **70%**。
**18% 就掉 0.7%，54%–70% 會掉多少沒人知道。**

這個數字直接決定 `E05` 主資料集的品質，而且掉幀是**靜默**的——
沒有 `B03` 的 `seq` 缺口偵測與 `B19` 的交叉驗證，根本不會有人發現。

> **這是「儀表抓到自己」的案例。** `B03` 的 `cross_check()` 推導出
> 「host ≤ device 恆成立，差額為正代表傳輸層故障」，`B19` 把它接進警報，
> 然後警報在自己的測試裡響了。**沒有那兩層，這個問題會一路帶到 Demo。**

## 範圍

**包含**
- 定位掉幀根因（目前懷疑：`readline()` + 解析 + 品質累積全在同一條 thread）
- 把「讀序列埠」與「解析／品質累積」解耦（例如讀取 thread 只做
  `readline()` 丟進 queue，另一條 thread 消費）
- 調高 pyserial 的 buffer 或改用 `read_until` / 非阻塞讀取
- **用 mock 在遞增頻寬下量掉幀率**：18% / 54% / 70% / 92%（錄音 dump）各一組
- 把量測結果寫進 `reports/B20_bridge_throughput.md`

**不包含**（避免範圍蔓延）
- 韌體側的送出邏輯（A 軌）
- 改協定（掉幀是實作問題不是協定問題）
- 前端顯示（`C09` 的範圍）

## 實作提示

- **先量再改。** 用 `mock_device.py` 的 `--fps` / `--dim` / `--mel`
  掃出「掉幀率 vs 頻寬」曲線，找到轉折點在哪。
- 懷疑清單（按可能性排序）：
  1. 讀取 thread 做太多事（解析 + `DropTracker` + `QualityAggregator` 都在裡面）
  2. pyserial 的預設 buffer 太小
  3. `Broadcaster.publish()` 在讀取 thread 裡對每個 client 做 `put_nowait`
  4. GIL 下 SSE handler thread 與讀取 thread 互相搶
- **不要用「掉幀率下降了」當唯一驗收**——要能說明**為什麼**下降，
  否則下次頻寬再上去又會回來。

## 驗收條件

- [ ] 在 mock 的 18% 頻寬下，`cross_check()` 的 `delta` 恆為 0（不再有傳輸層遺失）
- [ ] 在 70% 頻寬（8×8 + Mel）下掉幀率 < 0.1%
- [ ] 錄音 dump（92%）期間 ToF 掉幀可歸因於頻寬而非 bridge
      （`delta` 仍為 0，掉的是裝置端沒送，不是主機端沒收）
- [ ] `reports/B20_bridge_throughput.md` 有「掉幀率 vs 頻寬」的量測表與根因說明
- [ ] `B19` 的品質指標與端到端測試全部維持綠燈
