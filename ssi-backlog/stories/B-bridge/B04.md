# B04 — 時鐘對齊模型

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E1 訊號地基 |
| **估時** | 3 h |
| **前置** | `B01` |
| **阻擋** | `B06`, `B07` |
| **需要硬體** | 否 |
| **可平行於** | A/C/D 軌全部 |

## Story

**As a** 分析程式
**I want** 一個把 `device_us` 映射到主機時間的模型
**so that** 多個 session 能放到同一條時間軸，錄音能對齊 ToF

## 為什麼是這個順序

裝置時鐘從開機開始算，主機時鐘是 UTC。兩者的斜率也不完全一致（晶振誤差 ~50 ppm，一小時會漂 180 ms）。要對齊就要擬合一條線。

## 範圍

**包含**
- 收集 `(device_us, host_recv_time)` 配對
- 穩健擬合：滑動窗內取「最小延遲」點，再對這些點做線性回歸
- 輸出 `slope`、`offset`、`residual_p95`
- 模型持續更新，並可凍結成 session metadata

**不包含**（避免範圍蔓延）
- PING 主動取樣（B05）
- 寫進 HDF5（B07）

## 實作

**不要用普通最小平方法。** UART 延遲是**單邊**的：資料只會晚到，不會早到。OLS 會被排隊延遲拖偏，而且偏移量取決於當下的匯流排負載。

正確做法（最小延遲估計）：

```python
# 1. 把配對分成 1 秒一個 bucket
# 2. 每個 bucket 只保留 (host - device) 差值最小的那個點
#    → 這個點的排隊延遲最接近 0
# 3. 對這些「最乾淨」的點做最小平方回歸
```

驗收用**拍手測試**：對著裝置拍手，音訊會有明顯 peak，而手掌接近時 ToF 會看到距離驟降。兩個事件在物理上同時發生，對齊後的時間差就是你的實際誤差。

```python
# 存成 session metadata（T02 已預留欄位）
meta = {"clock_slope": 1.0000234, "clock_offset": 1756...,
        "clock_residual_p95": 0.0031}
```

## 驗收條件

- [ ] 對齊殘差 p95 < 5 ms
- [ ] 拍手測試 10 次，音訊 peak 與 ToF 事件時間差 < 20 ms
- [ ] 斜率落在 1 ± 200 ppm（超出範圍代表擬合有問題）
- [ ] T04 的 `--fault clock-jump` 下模型不崩潰，且標記異常
