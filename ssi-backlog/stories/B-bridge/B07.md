# B07 — HDF5 session writer

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E2 資料集 |
| **估時** | 3 h |
| **前置** | `T02`, `B06` |
| **阻擋** | `B08`, `D01`, `E05` |
| **需要硬體** | 否 |
| **可平行於** | A/C/D 軌全部 |

## Story

**As a** 分析流程
**I want** 把一個 session 的所有 trial 寫成符合 schema 的 HDF5
**so that** 離線分析不用重新解析序列埠 log

## 為什麼是這個順序

目前系統只存 WAV，ToF 資料顯示完就消失了。沒有持久化就沒有任何離線分析。

## 範圍

**包含**
- 依 T02 schema 建立 group 與 dataset
- metadata 寫入（含 B04 的時鐘模型）
- 增量寫入：每個 trial 結束就 flush，不要全部累積在記憶體
- session 異常中斷時已寫入的 trial 仍可讀

**不包含**（避免範圍蔓延）
- manifest（B08）
- metadata 表單 UI（C11）

## 實作

```python
with SessionWriter("data/sessions/2026-09-01_S01.h5", meta) as w:
    w.write_trial(idx=0, label="五", tof_A=..., tof_B=..., ...)
```

**增量 flush 不是效能考量，是資料保險。** 一次 session 錄 72 筆要 5 分鐘，中途當掉如果全部遺失，那 5 分鐘就白費了（而且戴法已經動過，重錄的資料跟前面不同質）。每個 trial 寫完就 `f.flush()`。

壓縮用 `gzip` level 4：ToF 資料重複性高，壓縮比通常 3–5×，而 level 4 的 CPU 成本可忽略。

用 context manager 確保異常時仍正確關檔。

## 驗收條件

- [ ] 100 個 trial 的 session 寫檔 < 3 秒，檔案 < 50 MB
- [ ] 寫到一半 kill -9，已寫入的 trial 仍可用 h5py 讀出
- [ ] 產出的檔案通過 T02 的 schema 驗證腳本
- [ ] 所有必填 attrs 齊全
