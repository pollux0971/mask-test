# B17 — HDF5 session 回放模式

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E2 資料集 |
| **估時** | 2 h |
| **前置** | `B07`, `T05` |
| **阻擋** | `C24`, `E08` |
| **需要硬體** | 否 |
| **可平行於** | A/C/D 軌全部 |

## Story

**As a** 前端開發者與 Demo 備援
**I want** 把存好的 session 重播成即時事件流
**so that** 我能離線開發前端，也能在硬體出事時當 Demo 備援

## 為什麼是這個順序

C 軌有 25 個 story，其中大半需要反覆調視覺化。每次都戴上裝置說話不現實。而且這也是 E08 失敗備援的核心。

## 範圍

**包含**
- `--replay-session <file.h5>` 從 HDF5 產生 SSE 事件
- 0.25× / 1× / 4× 速度、暫停、單步
- 可指定從第幾個 trial 開始
- SSE 事件帶 `replay: true` 標記

**不包含**（避免範圍蔓延）
- 前端播放控制列（C24）

## 實作

與 T05（重播原始 log）的差別：T05 重播的是**未解析的行**，適合測 B01 的解析器；B17 重播的是**已結構化的 session**，適合測 C 軌的視覺化與 D 軌的辨識。兩者都要有。

**`replay: true` 標記必須一路傳到前端並顯眼顯示。** 開發時你會反覆在真實與回放之間切換，沒有明顯標記遲早會搞混——更糟的是 Demo 時忘記切回真實模式。

回放要能餵給 D09 的辨識服務，這樣「用回放資料測試辨識準確率」就變得很容易。

## 驗收條件

- [ ] 回放時 panel 行為與即時模式一致
- [ ] 時序還原誤差 < 10 ms
- [ ] `replay: true` 標記在 SSE 事件中存在
- [ ] 可從任意 trial 開始
