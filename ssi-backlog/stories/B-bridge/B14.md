| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E3 音訊特徵 |
| **估時** | 3 h |
| **前置** | `T03` |
| **阻擋** | `D02`, `D09` |
| **需要硬體** | 否 |

## Story

**As a** D 軌辨識引擎
**I want** 從現有的 REC WAV dump 算出與裝置端規格一致的 log-Mel
**so that** 在 A12 完成前，整條辨識管線就能先跑通

## 為什麼是這個順序

**這是 A10/A11/A12 的完整備援。** 如果 esp-dsp 走不通，這條路徑一樣能做出 Demo，只是延遲 4 秒。更重要的是它現在就能做——不需要等任何韌體改動。

## 範圍

**包含**
- `voice/*.wav` → log-Mel，參數完全依 T03
- 接進 REC 完成的事件流
- 特徵寫回對應 trial 的 HDF5
- 與 A12 的裝置端輸出比對工具

**不包含**（避免範圍蔓延）
- 即時串流（那是 A12 的事）

## 實作

`bridge_server.py` 已經會把 WAV 存到 `voice/`（`save_wav()`），直接接上：

```python
import librosa
mel = librosa.feature.melspectrogram(
    y=y, sr=16000, n_fft=512, hop_length=256,
    n_mels=40, fmin=80, fmax=8000, htk=False, power=2.0)
log_mel = np.log10(np.maximum(mel, 1e-10))
```

**延遲拆解**（讓你知道預期是什麼）：
| 階段 | 時間 |
|---|---|
| 錄音 | 2.0 s |
| base64 傳輸 @46 KB/s | 1.9 s |
| 解碼 + MFCC | 0.1 s |
| **總計** | **~4.0 s** |

Demo 時要有分階段進度指示（C19），4 秒的等待若沒有回饋會顯得像當機。

比對工具（`tools/compare_mel.py`）在 A12 完成後用來驗收「相關係數 > 0.95」。
