# B03 — 掉幀偵測（seq 跳號）

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E1 訊號地基 |
| **估時** | 1.5 h |
| **前置** | `B01` |
| **阻擋** | `B19`, `C09` |
| **需要硬體** | 否 |
| **可平行於** | A/C/D 軌全部 |

## Story

**As a** 品質儀表
**I want** 主機端獨立算出掉幀率
**so that** 我能與韌體回報的數字交叉驗證

## 為什麼是這個順序

兩邊獨立算同一個數字，對不上就代表傳輸層有問題。這是很便宜的完整性檢查（A05 是另一半）。

## 範圍

**包含**
- 每個資料流（tof_A、tof_B、mic、mel）維護 last_seq
- 跳號時累計缺失數
- 滑動窗（30 秒）的掉幀率
- `$STATUS` 出現時重置（代表裝置重開機）

**不包含**（避免範圍蔓延）
- 前端顯示（C09）

## 實作

```python
class DropTracker:
    def observe(self, stream, seq):
        prev = self.last.get(stream)
        if prev is not None and seq != prev + 1:
            gap = (seq - prev - 1) % (2**32)
            if gap < 1000:            # 合理範圍內才算掉幀
                self.missing[stream] += gap
            else:
                self.resets[stream] += 1   # 太大 → 應該是重開機或解析錯誤
        self.last[stream] = seq
```

**`gap < 1000` 這個守衛很重要**：如果解析出錯讀到一個亂數 seq，沒有守衛的話掉幀計數會瞬間爆成幾百萬，整個儀表就沒用了。

滑動窗用 `collections.deque` 存 `(timestamp, missing_delta)`，比維護計數器差值簡單且不會累積誤差。

## 驗收條件

- [ ] T04 的 `--drop-rate 0.05` 下，偵測到的掉幀率落在 4–6%

- [ ] 裝置重開機（`$STATUS`）後計數正確重置，不產生假掉幀
