# B19 — SSE 事件擴充：品質與流程狀態

| 欄位 | 值 |
|---|---|
| **軌道** | B 主機橋接 |
| **Epic** | E4 儀表板 |
| **估時** | 2 h |
| **前置** | `B03`, `B04`, `B11` |
| **阻擋** | `C04`, `C09`, `C12` |
| **需要硬體** | 否 |
| **可平行於** | A/C/D 軌全部 |

## Story

**As a** 前端
**I want** 除了原始資料外，也收到已經算好的品質指標與流程狀態
**so that** 前端不用重複實作統計邏輯

## 為什麼是這個順序

掉幀率、對齊殘差、左右對稱性這些指標需要維護滑動窗與歷史，在前端做會讓 JS 變複雜且切換模式時狀態會遺失。放後端算一次，所有模式共用。

## 範圍

**包含**
- `quality` 事件（1 Hz）：掉幀率、有效 zone 比例、左右對稱性、對齊殘差、底噪、頻寬
- `trial` 事件：狀態機的每次狀態變更
- `session` 事件：session 開始/結束/進度
- 閾值判定（綠/黃/紅）也在後端做，讀 `config/quality_thresholds.json`

**不包含**（避免範圍蔓延）
- 前端顯示（C04、C09、C12）

## 實作

```json
{"type": "quality", "t": 1756...,
 "metrics": {
   "drop_rate":    {"value": 0.003, "level": "green"},
   "valid_zones":  {"value": 0.94,  "level": "green"},
   "symmetry":     {"value": 0.21,  "level": "yellow",
                    "hint": "左右不對稱，感測器 A 偏遠，調整骨架"},
   "clock_resid":  {"value": 0.0031,"level": "green"},
   "noise_floor":  {"value": 142,   "level": "green"},
   "bandwidth":    {"value": 0.37,  "level": "green"}}}
```

**`hint` 欄位直接帶診斷建議**，而不是讓前端維護一份「哪個指標紅了要顯示什麼訊息」的對照表。指標的意義後端最清楚，建議也應該由後端給。

閾值放 `config/quality_thresholds.json`（T06 已規劃為共用可寫目錄），調閾值不需要改程式。
