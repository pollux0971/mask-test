# E01 — Bring-up 冒煙測試（協定 v2 上機）

| 欄位 | 值 |
|---|---|
| **軌道** | E 硬體實驗 |
| **Epic** | E1 訊號地基 |
| **估時** | 2 h |
| **前置** | `A04`, `A06`, `B01` |
| **阻擋** | `T05`, `E02`, `E03` |
| **需要硬體** | **是** |
| **可平行於** | D 軌全部 |

## Story

**As a** 全體軌道
**I want** 確認協定 v2 韌體在真實硬體上穩定運作
**so that** 後續所有實驗建立在可靠的基礎上

## 為什麼是這個順序

**這是第一個真實硬體的同步點。** A 軌與 B 軌在此之前都是各自對著契約開發，這裡第一次真接。所有整合問題會在這一刻集中爆發，所以要留緩衝。

## 範圍

**包含**
- 燒錄協定 v2 韌體，連上真實 bridge
- 連續運作 30 分鐘，檢查掉幀、heap、時序
- 拍手測試驗證時鐘對齊
- 錄一段原始 log 供 T05 使用

**不包含**（避免範圍蔓延）
- Mel（A12 完成後另做一次）

## 實作

檢查清單：

- [ ] `$STATUS` 顯示 `proto=2` 且 fw sha 正確
- [ ] 4×4 實測幀率 ≥ 29 Hz（A04 的修正生效）
- [ ] 掉幀率 < 1%，韌體與主機端數字一致（A05 vs B03）
- [ ] 30 分鐘 heap 下降 < 2 KB
- [ ] 時鐘對齊殘差 p95 < 5 ms（B04）
- [ ] 拍手測試 10 次，音訊與 ToF 事件時間差 < 20 ms
- [ ] 錄下 5 分鐘原始 log 存進 `logs/`

**留 2 小時緩衝。** 整合的第一次通常不會一次過——通常是格式細節（欄位順序、分隔符號）或時序假設不一致。這些都很快能修，但要有時間修。

## 驗收條件

- [ ] 檢查清單全部通過
- [ ] 原始 log 已錄並可供 T05 重播
- [ ] 任何發現的契約歧義已更新回 `CONTRACTS.md`

## 完成定義

- [ ] 全部驗收條件打勾
- [ ] commit 訊息含 `E01`
- [ ] 若動到跨軌介面，`CONTRACTS.md` 已同步更新並通知其他軌道
