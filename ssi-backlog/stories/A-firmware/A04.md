# A04 — 修正 ToF 輪詢週期

| 欄位 | 值 |
|---|---|
| **軌道** | A 韌體 |
| **Epic** | E1 訊號地基 |
| **估時** | 1.5 h |
| **前置** | 無（可立即開始） |
| **阻擋** | `A05`, `E01` |
| **需要硬體** | 是 |
| **可平行於** | 全部 |

## Story

**As a** 資料蒐集流程
**I want** ToF 主迴圈的輪詢頻率遠高於感測器輸出頻率
**so that** 4×4 @ 30 Hz 模式不會不規則地丟掉三分之一的幀

## 為什麼是這個順序

這是獨立於協定的純 bug 修正，可以最先做、也可以最後做，不阻擋任何人。但它必須在 E01 上機冒煙測試前完成，否則第一批真實資料就是壞的。

## 範圍

**包含**
- `vTaskDelay(pdMS_TO_TICKS(50))` → `pdMS_TO_TICKS(5)`
- 量測實際幀率與幀間隔標準差

**不包含**（避免範圍蔓延）
- 中斷驅動改寫（若 5 ms 輪詢就夠，不做）
- FREERTOS_HZ 調整（同上）

## 實作

目前：

```c
while (1) {
    for (i...) { check_data_ready(); get_ranging_data(); }
    vTaskDelay(pdMS_TO_TICKS(50));   /* 20 Hz 輪詢 vs 30 Hz 感測器 */
}
```

`CONFIG_FREERTOS_HZ=100` → tick = 10 ms → `pdMS_TO_TICKS(5)` 實際會是 1 tick = 10 ms，仍是 100 Hz 輪詢，對 30 Hz 感測器夠了（3.3× 過取樣）。

先做這個最小改動並量測。**只有在幀間隔標準差 > 3 ms 時才考慮升級方案**：

- 方案 B：`CONFIG_FREERTOS_HZ` 100 → 1000（tick 1 ms，但全系統 context switch 開銷上升）
- 方案 C：接 VL53L7CX 的 INT 腳走中斷（最乾淨，但要多兩條線）

**先量再改。** 很可能 10 ms 輪詢就已經達標了，不需要動 FreeRTOS 設定。

## 驗收條件

- [ ] 4×4 模式兩顆實測幀率皆 ≥ 29 Hz
- [ ] 8×8 模式實測幀率 ≥ 9.8 Hz
- [ ] 幀間隔標準差 < 3 ms（由主機端 `t_us` 差分計算）
- [ ] 量測結果記錄在 `reports/A04_polling.md`，含改前改後對照
