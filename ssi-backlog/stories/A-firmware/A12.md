# A12 — log-Mel 計算與 $F 輸出

| 欄位 | 值 |
|---|---|
| **軌道** | A 韌體 |
| **Epic** | E3 音訊特徵 |
| **估時** | 4 h |
| **前置** | `A11`, `A03` |
| **阻擋** | `B01`, `C08` |
| **需要硬體** | 是 |
| **可平行於** | B/C/D 軌全部 |

## Story

**As a** 辨識引擎
**I want** 裝置端串流 40 維 log-Mel
**so that** 音訊特徵與 ToF 同步、低延遲

## 為什麼是這個順序

`$MIC` 的 RMS 只能區分「有沒有出聲」。要區分「五」和「一」需要頻譜。而串原始音訊會吃掉 92% 頻寬——Mel 只要 12 KB/s。

## 範圍

**包含**
- 在 `mic_task` 中對每個音框做 Hann → FFT → power → mel → log
- 輸出 `$F,<seq>,<t_us>,<m0..m39>`，int16 = log_mel × 100
- 與 `$M` 共用同一個 `seq` 與 `t_us`

**不包含**（避免範圍蔓延）
- hop 改 256（A14）
- MEL 開關指令（A13）

## 實作

檔案：`main/bone_mic.c`

管線：

```
512 samples (int16) → 轉 float 並套 Hann 窗
                    → dsps_fft2r_fc32 (512, 複數 in-place)
                    → power[k] = re² + im²，k = 0..256
                    → mel[m] = Σ filterbank[m] · power[]
                    → log10(max(mel, 1e-10)) × 100 → int16
```

**先做 512 hop（無重疊），跟現有的 `MIC_FRAME_SAMPLES` 一致。** 這樣 A12 不會同時改動兩個變因，出問題好定位。A14 再改 hop。

Hann 窗也預先算成靜態表（512 個 float = 2 KB）。

輸出行長：40 × 6 字元 ≈ 250 bytes × 31 Hz ≈ 7.8 KB/s。加上 `$T`（8.7 KB/s）與 `$M`（0.5 KB/s）總計 17 KB/s，佔 46 KB/s 的 37%。仍有餘裕，但 A14 把 hop 減半後 `$F` 會翻倍到 15.6 KB/s，總計 25 KB/s（54%）——**這是頻寬的實際上限，A14 要重新驗證**。

## 驗收條件

- [ ] `$F` 與 `$M` 的 `seq` 一一對應
- [ ] 對 1 kHz 正弦波，能量集中在對應的 mel band
- [ ] 裝置端 Mel 與主機端 librosa 對同一段 WAV 的結果，相關係數 > 0.95
- [ ] 啟用 Mel 後 ToF 掉幀率仍 < 1%
- [ ] `mic_task` 的 stack high-water mark 仍有 > 1 KB 餘裕
