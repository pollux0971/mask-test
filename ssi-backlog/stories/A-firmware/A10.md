# A10 — esp-dsp 整合探針（FFT 正確性）

| 欄位 | 值 |
|---|---|
| **軌道** | A 韌體 |
| **Epic** | E3 音訊特徵 |
| **估時** | 3 h |
| **前置** | 無（可立即開始） |
| **阻擋** | `A11`, `A12` |
| **需要硬體** | 是 |
| **可平行於** | 全部 |

## Story

**As a** A 軌開發者
**I want** 先用最小程式確認 esp-dsp 的 FFT 在這塊板子上能跑且結果正確
**so that** 我在投入 Mel 實作前就知道這條路通不通

## 為什麼是這個順序

這是一個 **spike**（技術探針），不是功能。它的產出是一個 yes/no 決策：esp-dsp 能不能用？若三小時內跑不出正確的 FFT，就走 B14 的主機端路線，A11/A12 直接取消。**先花三小時買到這個答案，比花兩天才發現走不通划算。**

## 範圍

**包含**
- 加入 `espressif/esp-dsp` 依賴
- 對已知的合成正弦波做 512 點 FFT
- 驗證峰值出現在正確的 bin
- 量測單次 FFT 耗時

**不包含**（避免範圍蔓延）
- Mel 濾波器
- 串流輸出
- 整合進 mic_task

## 實作

```
idf.py add-dependency "espressif/esp-dsp"
```

```c
/* 產生 1 kHz @ 16 kHz 取樣的測試訊號 */
for (int i = 0; i < 512; i++)
    x[i*2] = sinf(2*M_PI*1000*i/16000), x[i*2+1] = 0;

dsps_fft2r_init_fc32(NULL, 512);
int64_t t0 = esp_timer_get_time();
dsps_fft2r_fc32(x, 512);
dsps_bit_rev_fc32(x, 512);
int64_t dt = esp_timer_get_time() - t0;
/* 1 kHz @ 16 kHz, N=512 → bin = 1000 * 512 / 16000 = 32 */
```

**決策點**：
- FFT 正確且 < 500 µs → 繼續 A11、A12
- FFT 正確但 > 2 ms → 勉強可行（16 ms hop 的 12%），但要在 A15 密切監控
- 跑不起來或結果錯誤 → **停止，改走 B14**，把 A11/A12 從 backlog 移除
