# A05 — 掉幀計數器

| 欄位 | 值 |
|---|---|
| **軌道** | A 韌體 |
| **Epic** | E1 訊號地基 |
| **估時** | 1 h |
| **前置** | `A01`, `A04` |
| **阻擋** | `A06` |
| **需要硬體** | 是 |
| **可平行於** | B/C/D 軌全部 |

## Story

**As a** 品質儀表
**I want** 韌體自己統計掉了幾幀
**so that** 我能與主機端由 `seq` 推算的數字交叉驗證

## 為什麼是這個順序

兩邊獨立算同一個數字，對不上就代表傳輸層有問題（buffer overflow、UART 錯誤）。這是很便宜的完整性檢查。

## 範圍

**包含**
- 偵測 `check_data_ready()` 連續兩次 ready 之間的時間間隔異常
- 偵測 `get_ranging_data()` 回傳非 0 的次數
- 累計計數器，供 A06 心跳行輸出

**不包含**（避免範圍蔓延）
- 主機端的 seq 跳號偵測（B03）

## 實作

韌體端的「掉幀」有兩種來源，要分開計數：

```c
static uint32_t s_drop_notready[NUM_SENSORS];  /* 該來的幀沒來 */
static uint32_t s_drop_error[NUM_SENSORS];     /* I²C 讀取失敗 */
```

第一種靠時間推：若 `t_us - last_t_us > 1.5 * expected_period`，補記 `(delta / period) - 1` 個掉幀。
第二種直接在 `status != 0` 的分支 `++`。

**這兩個數字的意義完全不同**：`drop_error` 上升代表 I²C 訊號品質問題（拉線太長、上拉電阻不對）；`drop_notready` 上升代表 CPU 來不及輪詢或感測器本身沒出幀。診斷時要能分辨。

## 驗收條件

- [ ] 正常運作 5 分鐘，兩個計數器都為 0
- [ ] 故意把輪詢改回 50 ms，`drop_notready` 明顯上升
- [ ] 拔掉一顆感測器的 SDA，`drop_error` 上升而另一顆不受影響
