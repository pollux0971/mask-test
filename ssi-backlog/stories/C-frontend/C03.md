# C03 — 模式路由與跨模式狀態保存

| 欄位 | 值 |
|---|---|
| **軌道** | C 前端 |
| **Epic** | E4 儀表板 |
| **估時** | 3 h |
| **前置** | `C02` |
| **阻擋** | `C05`, `C11`, `C15`, `C22`, `C24` |
| **需要硬體** | 否 |
| **可平行於** | A/B/D 軌全部 |

## Story

**As a** 使用者
**I want** 切走再切回來時，模式維持我離開時的狀態
**so that** 我在監測模式調好的基線與色階不會因為去測驗模式一趟就消失

## 為什麼是這個順序

**這個 story 決定了整個前端的架構是否可持續。** 如果模式切換等於重建 DOM，那 C05–C24 每個 story 都要處理「重新初始化」的問題，複雜度會爆炸。

## 範圍

**包含**
- 事件匯流排：SSE 事件廣播給所有模式，不論是否顯示
- 模式生命週期：`init()` 一次、`onEnter()` / `onLeave()` 每次切換
- 隱藏的模式停止繪製但繼續累積資料
- URL hash 反映當前模式（`#/monitor`），可直接連結

**不包含**（避免範圍蔓延）
- 各模式的具體狀態內容

## 實作

**核心架構決定：資料層與模式層分離。**

```
SSE ──► bus.js ──┬──► dataStore（環形緩衝，永遠在跑）
                 └──► 當前模式的 render()（只有可見的模式跑）
```

測驗模式（C15）需要即時 ToF 與 Mel，監測模式（C05）也需要。如果資料層綁在模式上，切換模式就會中斷資料流——而 B19 的品質指標需要連續的滑動窗，中斷會讓它重新暖機。

```js
export const Mode = {
  init(root) {},        // 只呼叫一次，建立 DOM
  onEnter() {},         // 每次切入：恢復繪製迴圈
  onLeave() {},         // 每次切出：暫停 rAF，但不清狀態
  onData(evt) {},       // 永遠收（不論可見與否），但可自行決定是否處理
};
```

**隱藏時要停 `requestAnimationFrame`，不要只是 `display:none`。** 五個模式的 canvas 同時繪製會吃掉大量 CPU，而 Demo 時筆電通常還在跑投影。

URL hash 讓你能在 Demo 前先開好 `#/quiz` 的分頁，切過去就是準備好的畫面。

## 驗收條件

- [ ] 在監測模式設好基線 → 切到測驗 → 切回來，基線仍在
- [ ] 隱藏的模式其 rAF 已停止（用 DevTools Performance 確認）
- [ ] SSE 中斷重連後所有模式都恢復
- [ ] `#/quiz` 直接開啟測驗模式
- [ ] 五模式同時存在時，idle CPU < 15%
