# C09 — 監測模式：訊號品質儀表板

| 欄位 | 值 |
|---|---|
| **軌道** | C 前端 |
| **Epic** | E4 儀表板 |
| **估時** | 3 h |
| **前置** | `C03`, `B19` |
| **阻擋** | 無 |
| **需要硬體** | 否 |
| **可平行於** | A/B/D 軌全部 |

## Story

**As a** 研究者
**I want** 一組永遠可見的品質指標，戴上裝置的當下就知道戴對了沒
**so that** 我不會蒐集完 200 筆才發現戴歪了

## 為什麼是這個順序

**這是把「事後驗證」變成「事前把關」的關鍵 story。** 實驗 A 的對稱性判定、實驗 B 的重複性，都可以在戴裝置的當下就邊調邊看，而不是錄完一小時再算出來說要重來。

## 範圍

**包含**
- **六個**指標的完整面板：`drop_rate`（掉幀）、`valid_zones`（有效 zone）、
  `symmetry`（左右對稱）、`clock_resid`（對齊殘差）、`noise_floor`（底噪）、
  `bandwidth`（**鏈路使用率**）

  > ⚠️ **原文寫「七個」是錯的。** 這份 story 寫於 `B19` 之前，用的是舊假設。
  > 已凍結的 `CONTRACTS.md` §4.2 與 `B19` 實際送出的 `quality` 事件都是
  > **六個**——**沒有**「基線穩定度」與「即時 SNR」，但**多了 `bandwidth`**。
  > 一律以 §4.2 與線上實際封包為準，不要為了湊七個而發明不存在的指標。
- 綠/黃/紅三色，紅燈時顯示 B19 給的 `hint`
- 每個指標的 60 秒趨勢迷你圖（sparkline）
- 「開始錄製」按鈕在有紅燈時彈確認

**不包含**（避免範圍蔓延）
- 指標計算（B19 全部在後端做）

## 實作

| 指標 | 綠 | 黃 | 紅 |
|---|---|---|---|
| 掉幀率 | < 1% | 1–5% | > 5% |
| 有效 zone | > 90% | 70–90% | < 70% |
| **左右對稱性** | < 15% | 15–30% | > 30% |
| 音訊底噪 | < 200 | 200–500 | > 500 |
| 對齊殘差 | < 5 ms | 5–15 ms | > 15 ms |

**sparkline 比單一數值有用得多。** 對稱性 20%（黃燈）如果趨勢是往下走，代表你正在把骨架調對；如果在往上飄，代表裝置正在滑動。同一個數字，兩種完全不同的處置。

前端只負責顯示，所有判定邏輯在 B19。這樣調閾值只要改 JSON。
