# D09 — 即時辨識服務

| 欄位 | 值 |
|---|---|
| **軌道** | D 分析引擎 |
| **Epic** | E6 Demo |
| **估時** | 2.5 h |
| **前置** | `D07`, `D08`, `B06` |
| **阻擋** | `C16` |
| **需要硬體** | 否 |
| **可平行於** | A/B/C 軌全部 |

## Story

**As a** 測驗模式前端
**I want** 一個接收擷取片段、回傳三軌結果的 API
**so that** 前端不用知道特徵與 DTW 的細節

## 為什麼是這個順序

把辨識包成服務，前端與分析引擎的介面就只有一個 JSON。C 軌與 D 軌可以完全獨立開發與測試。

## 範圍

**包含**
- `POST /recognize`（body: trial 片段或 trial_id）→ `TriResult` JSON
- 樣板熱載入（換 enrollment 不需重啟）
- `GET /templates` 列出已載入的樣板組
- 延遲量測與回報

**不包含**（避免範圍蔓延）
- 前端顯示

## 實作

```json
{"classes": ["八","五","一","啊","四","好","停","不要"],
 "d_tof": [2.1, 0.3, 1.8, ...], "d_mel": [1.9, 1.1, ...],
 "reject_tof": false, "reject_mel": false,
 "latency_ms": {"feature": 12, "dtw": 47, "total": 61}}
```

**`latency_ms` 的分階段回報很實用**：Demo 卡頓時你需要知道是特徵慢還是 DTW 慢。而且這個數字會進論文（「系統端到端延遲 61 ms」是一個具體的工程指標）。

樣板熱載入：C20 的 enrollment 完成後直接切換，不用重啟服務——Demo 前的準備時間很珍貴。

服務可以直接跑在 `bridge_server.py` 的執行緒裡（它已經是 ThreadingHTTPServer），不需要另開一個 process。

## 驗收條件

- [ ] 端到端延遲 < 100 ms（不含錄音與傳輸）
- [ ] 樣板熱載入不中斷服務
- [ ] 延遲分階段回報
- [ ] 可用回放資料（B17）測試
