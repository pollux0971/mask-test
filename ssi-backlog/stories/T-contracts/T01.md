| 欄位 | 值 |
|---|---|
| **軌道** | T 契約層 |
| **Epic** | E1 訊號地基 |
| **估時** | 2 h |
| **前置** | 無（可立即開始） |
| **阻擋** | `A01`, `A03`, `B01`, `T04` |
| **需要硬體** | 否 |
| **可平行於** | T02, T03（三份規格可同時寫） |

## Story

**As a** 平行開發的四條軌道
**I want** 一份凍結的序列埠協定規格
**so that** 韌體與主機端可以各自對著同一份文件開發，不用互相等待

## 為什麼是這個順序

這是整個平行開發的第一顆骨牌。協定沒定，A 軌不知道要印什麼、B 軌不知道要解析什麼、T04 的模擬器不知道要吐什麼。這份文件寫完的當下，A/B/C/D 四條軌道同時解鎖。

## 範圍

**包含**
- `CONTRACTS.md` 的「協定 v2」章節：每一種 `$` 行的欄位、型別、單位、範圍
- 無效值的表示方式（`-1`）與適用情境
- 主機→裝置的指令格式
- 版本協商機制（`$STATUS` 的 `proto=`）
- 至少 3 行真實範例（含極端值）

**不包含**（避免範圍蔓延）
- 任何程式碼實作
- Mel 相關欄位的細節（T03 負責，此處只保留 `$F` 的佔位）

## 實作

把 `SSI_Phase0_Epic_Backlog.md` 附錄的協定草案搬進 `CONTRACTS.md`，並補上這些草案沒寫清楚的地方：

| 待決事項 | 建議決定 |
|---|---|
| `t_us` 溢位 | `esp_timer_get_time()` 是 int64 µs，約 29 萬年才溢位，不處理 |
| `seq` 溢位 | `uint32` @ 30 Hz 約 4.5 年，但重開機會歸零 → 主機以 `$STATUS` 為 session 邊界 |
| signal rate 縮放 | `signal_per_spad / 100`，四捨五入成整數 |
| 行長上限 | 8×8 模式 `$T` 最長 = 5 + 2×64×6 ≈ 780 bytes → 主機端 readline buffer 要 ≥ 1024 |
| 浮點格式 | 一律定點整數，避免 locale 與 printf 浮點成本 |

**行長上限那條要特別注意**：8×8 加上 signal rate 之後單行接近 800 bytes，@460800 baud 一行要 17 ms 才送得完，而 8×8 是 10 Hz（100 ms 一幀）——還來得及，但兩顆同時就吃掉 34%。寫進規格讓 B 軌知道要留 buffer。
