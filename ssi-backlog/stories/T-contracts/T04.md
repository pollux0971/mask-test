# T04 — Mock Device：合成資料產生器

| 欄位 | 值 |
|---|---|
| **軌道** | T 契約層 |
| **Epic** | E1 訊號地基 |
| **估時** | 4 h |
| **前置** | `T01` |
| **阻擋** | `B01`, `C01`, `C05` |
| **需要硬體** | 否 |
| **可平行於** | A 軌全部 |

## Story

**As a** B 軌與 C 軌開發者
**I want** 一個假裝置，從 pty 或 socket 吐出符合協定 v2 的資料
**so that** 我不用等韌體寫完、不用接硬體、不用戴上裝置就能開發整個主機端與前端

## 為什麼是這個順序

**這是整份 backlog 投報率最高的一個 story。** 沒有它，B/C 軌要等 A 軌燒錄成功才能動工，四條軌道退化成兩條。有了它，A 軌可以慢慢除錯 esp-dsp，B/C/D 三軌完全不受影響地全速前進。

## 範圍

**包含**
- 以 `pty` 建立虛擬序列埠，bridge 端不需改任何程式碼就能連上
- 產生 `$T`（雙感測器）、`$M`、`$H`、`$STATUS` 四種行
- 可設定的 ToF 幀率、Mel 開關、解析度
- 可注入的故障：掉幀、無效 zone、時間戳跳動、斷線
- 幾種可切換的合成唇形場景（靜止／圓唇／展唇／隨機）

**不包含**（避免範圍蔓延）
- 真實的生理訊號模型（合成資料只需結構正確，不需物理擬真）
- 音訊 WAV dump 模擬（B17 的 replay 才需要）

## 實作

```python
# tools/mock_device.py
python3 tools/mock_device.py --fps 30 --dim 4 --scenario round --drop-rate 0.02
# → 印出 /dev/pts/N，接著：
python3 monitor/bridge_server.py --port /dev/pts/N
```

合成場景建議做成一個簡單的參數化模型即可：

```python
SCENARIOS = {
    "idle":   lambda t, z: 17.0 + 0.15 * noise(),
    "round":  lambda t, z: 17.0 - 3.0 * bump(t) * center_weight(z) + 0.15*noise(),
    "spread": lambda t, z: 17.0 + 1.2 * bump(t) * edge_weight(z)   + 0.15*noise(),
}
```

`bump(t)` 是一個 400 ms 的半正弦，`center_weight(z)` 讓中央 zone 反應強、邊角弱。

**故障注入不是可選功能。** C 軌的品質儀表（C09）與 B 軌的掉幀偵測（B03）都需要「能重現的壞資料」來驗收——真實硬體的掉幀是隨機的，沒辦法拿來寫測試。
