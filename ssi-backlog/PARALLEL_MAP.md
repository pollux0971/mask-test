# 平行開發地圖

93 個 atomic story · 總工時 188 h（23.6 人天）· 6 條軌道

---

## 1. 平行化的前提：契約優先

平行開發最常見的失敗不是技術問題，是**兩個人對同一個介面有不同想像**，各自寫完才發現接不起來。

這份 backlog 用一個機制避免它：**T 軌的六個 story 先把所有跨軌介面凍結成文件**，之後每條軌道都只對著文件開發，不需要互相詢問。

| 契約 | 凍結什麼 | 解鎖誰 |
|---|---|---|
| `T01` 協定 v2 | 序列埠每一行的欄位、型別、單位 | A 軌與 B 軌可各自開發 |
| `T02` HDF5 schema | 資料集結構與 attrs | D 軌可用假資料全速開發 |
| `T03` 特徵規格 | Mel 參數、正規化、通道順序 | A12 與 B14 兩條路線可互驗 |
| `T04` Mock Device | **一個假裝置** | **B/C/D 三軌完全脫離硬體** |
| `T06` 目錄劃分 | 誰擁有哪些檔案 | 消除 merge conflict |

### T04 是整份 backlog 投報率最高的 story

沒有它，B/C 軌必須等 A 軌燒錄成功才能動工，六條軌道退化成兩條。
有了它，A 軌可以慢慢跟 esp-dsp 搏鬥，B/C/D 三軌完全不受影響地全速前進。

**4 小時的投入，換來 136 小時的工作可以提前開始。**

## 4. 關鍵路徑

這 15 個 story 串成一條鏈，總長 **34.5 h（4.3 天）**。
**不論投入多少人力，專案都不可能比這條鏈更快完成。**

```
├─► T01 [ 2.0h] 凍結協定 v2 規格
├─► T04 [ 4.0h] Mock Device：合成資料產生器
├─► B01 [ 2.0h] 解析協定 v2 行格式
├─► B04 [ 3.0h] 時鐘對齊模型
├─► B06 [ 3.0h] 多模態時間對齊器
├─► B07 [ 3.0h] HDF5 session writer
├─► B09 [ 1.5h] Session metadata API
├─► B10 [ 1.5h] Session baseline 自動錄製
├─► C11 [ 2.0h] 錄製模式：session 設定表單
├─► C12 [ 2.5h] 錄製模式：trial 提示卡與倒數
├─► C13 [ 2.0h] 錄製模式：進度與 trial 清單
├─► E05 [ 4.0h] 主資料集蒐集
├─► E06 [ 1.0h] Enrollment 與 LOOCV 驗收
├─► E07 [ 2.0h] Demo 排練 ×3
└─► E08 [ 1.0h] 失敗備援演練
```

**這條路徑告訴你三件事：**

1. **關鍵路徑穿過 B 軌**（B01→B04→B06→B07→B09→B10 共 14 h）。B 軌卡住，全專案就卡住——它應該優先分配資源。
2. **C11→C12→C13 在關鍵路徑上**，因為 `E05`（主資料集蒐集）需要能用的錄製介面。前端的錄製模式不是「錦上添花」，它擋著資料蒐集。
3. **最後四個是 E 軌**（E05→E06→E07→E08 共 8 h），這些是純人工時間，無法壓縮也無法平行。

反過來說，**不在關鍵路徑上的 story 有很大的排程彈性**——例如 A 軌的 A10–A14（Mel，11 h）完全不在關鍵路徑上，卡住了也不影響交付日期，因為 B14 是它的備援。

## 5. 不同人力下的實際工期

以貪婪列表排程模擬（同一時間只有一個人能碰硬體）：

| 人力 | 工期 | 相對單人 | 人力效率 | 適合情境 |
|---|---|---|---|---|
| 1 | **23.6 天** | 1.00× | 100% | 你自己，逐項推進 |
| 2 | **14.1 天** | 1.67× | 83% | 你 + 一個 Claude Code agent |
| 3 | **10.7 天** | 2.20× | 73% | 你 + 兩個 agent（**建議**） |
| 4 | **9.9 天** | 2.37× | 59% | 你 + 三個 agent |
| 5 | **10.1 天** | 2.34× | 47% | 報酬明顯遞減 |

**3 個工作單元是甜蜜點**：10.7 天，人力效率 73%。
加到 4 個只省 0.8 天，效率掉到 59%。

**注意第 5 個工作單元反而更慢**（10.1 天 vs 4 個的 9.9 天）。
這不是模擬誤差，是**硬體瓶頸**：25 個 story 需要實體板子，全部排在 W0 身上。
再多的人也只是等 W0 燒錄完、實驗做完——多出來的人力無事可做，
而排程的碎片化反而讓某些依賴鏈延後。

**這個現象的實務意義：與其加第 4、第 5 個 agent，不如想辦法縮短 W0 的硬體工作。**
例如先把 A 軌的 15 個 story 一次燒錄驗證完（省去反覆燒錄的固定成本），
或準備第二套板子讓 A 軌與 E 軌能真正平行。

### 不要固定分配軌道

我也模擬了「一人一軌」的固定分配：

| 配置 | 工期 |
|---|---|
| 3 人彈性接單 | 10.7 天 |
| 3 人固定軌道（T+A+E / B / C+D） | 14.5 天 |
| 4 人固定軌道 | 10.2 天 |

**固定分配慢 1.4 倍。** 原因是各軌工時嚴重不均（C 軌 57.5 h vs T 軌 13 h），
負責 T 軌的人做完就閒著，而 C 軌的人做到最後。

**正確做法：每個人（或 agent）做完一個 story 就從「當前可開工清單」裡挑下一個**，不分軌道。
下一節的檔案所有權表讓這件事不會造成衝突。

## 6. 檔案所有權（避免衝突）

彈性接單的前提是**同一時間不會有兩個 story 改到同一個檔案**。以下劃分保證這一點：

| 目錄／檔案 | 擁有者 | 說明 |
|---|---|---|
| `vl53l7cx_test/main/*.c`, `*.h` | **A 軌獨佔** | 韌體，只有 A01–A15 會碰 |
| `vl53l7cx_test/monitor/bridge_server.py` | **B 軌獨佔** | B01–B19 |
| `host/` | **B 軌獨佔** | capture / storage / clock |
| `vl53l7cx_test/monitor/panel/` | **C 軌獨佔** | 且**一模式一檔**，C 軌內部也不衝突 |
| `analysis/` | **D 軌獨佔** | features / similarity / experiments / reporting |
| `tools/` | **T 軌** | mock device |
| `config/*.json` | 共用**唯讀為主** | 純資料，衝突也只是 JSON 合併 |
| `CONTRACTS.md` | **共用，需協調** | 改動要通知全體 |

### C 軌內部的防衝突設計

C 軌 25 個 story 是最大的一軌，如果都改 `panel.html` 就會天天衝突。所以 `C01` 的第一件事就是**拆檔**：

```
monitor/panel/js/modes/
├── monitor.js    ← C05–C10 專屬
├── record.js     ← C11–C14 專屬
├── quiz.js       ← C15–C21 專屬
├── validate.js   ← C22–C23 專屬
└── replay.js     ← C24 專屬
```

**一模式一檔不是美學選擇，是平行化的必要條件。** C05（監測熱力圖）與 C16（測驗評分）可以同時開發，因為它們碰不到彼此的檔案。

## 7. 同步點

這些是「多條軌道必須匯合」的時刻，要預留緩衝：

| # | 同步點 | 匯合的軌道 | 風險 | 緩衝建議 |
|---|---|---|---|---|
| SP1 | `T01`–`T06` 契約凍結 | 全體 | 契約有歧義 → 後續返工 | 花足 13 h，不要趕 |
| SP2 | `E01` 首次真硬體整合 | A + B | **整合問題集中爆發** | **+2 h 緩衝** |
| SP3 | `A10` esp-dsp 探針 | A | 走不通 → A11–A14 取消 | 硬性 3 h 上限 |
| SP4 | `D13` Silhouette 出爐 | D | **可能推翻專案前提** | 見下方 |
| SP5 | `E06` Enrollment LOOCV | 全體 | Demo 會不會翻車 | 留重錄時間 |

### SP4 是最重要的同步點

`D13` 會給出 `S(ToF_only)` 這個數字。如果它接近 0 而 `S(Mel)` 很高，
代表**準確率全部來自麥克風，ToF 沒有貢獻**——這會動搖整個研究前提。

這個數字應該**盡早取得**。從波次圖看，`D13` 的依賴是 D01/D02/D03，
而這三個只需要 T02/T03 的契約 + 一批真實資料。
**建議在 `E05` 完成後立刻跑 D13，不要等其他實驗。**

若真的成立，仍是有價值的 negative result：寫進 limitations，
並把論證重心轉向「ToF 在 silent 模式下的獨立價值」（`D13` 的 silent 欄位、`D17` 的 silent 對照圖）。

## 10. 用 Claude Code 平行開發的實務建議

每個 story 檔案已經寫成**可以直接餵給 agent 的規格**：有範圍、有實作提示、有驗收條件。

### 開場提示範本

```
讀 CONTRACTS.md 與 stories/B-bridge/B06.md。
只實作 B06 這一個 story，不要順手改別的。
你只能修改 host/ 目錄下的檔案（見 T06 的檔案所有權）。
完成後逐條核對 B06 的驗收條件，並列出哪些通過、哪些沒有。
如果你發現 CONTRACTS.md 有歧義，停下來問我，不要自己決定。
```

### 三條規則

1. **一個 agent 一次只做一個 story。** 讓 agent「順便把 B07 也做了」是衝突的開始——B07 的依賴可能還沒完成。
2. **檔案所有權寫進提示。** agent 看不到別人在改什麼，只能靠邊界約束。
3. **契約歧義要回報而非自行決定。** 兩個 agent 對同一個歧義做出不同決定，就是 SP2 整合爆炸的來源。

### 適合交給 agent 的 story

純函式、有明確驗收條件、不需要視覺判斷的最適合：

- **D 軌幾乎全部**（D01–D08、D10–D20）— 純 Python 函式，輸入輸出明確
- **B 軌大部分**（B01、B03、B06、B07、B08、B14、B15）— 有 mock device 可測
- **T04 / T05** — 規格明確的工具程式

### 不適合交給 agent 的

- **A 軌全部** — 需要燒錄到實體板子並用示波器/相機驗證
- **E 軌全部** — 需要你本人戴上裝置
- **C06、C09、C16、C25** — 需要視覺判斷「這樣看起來對不對」
- **T01–T03 契約** — 需要領域知識做取捨決策

## 12. 平行度的實際限制

模擬顯示理論最大平行度是 5.5×，但實際拿不到，原因有三：

1. **硬體只有一套。** 25 個 story 需要實體板子，同一時間只有一個人能用。這也是為什麼 A 軌與 E 軌應該由同一個人負責。
2. **關鍵路徑 34.5 h。** 這是硬下限，加人也不會更快。
3. **E 軌是人工時間。** E04 的 20 次戴脫、E05 的 4 小時資料蒐集，這些是物理時間，無法壓縮。

所以實際的甜蜜點是 3 個工作單元、10.7 天。
