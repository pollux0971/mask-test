# 鍵盤操作稽核報告

> 由 `esp-mask-test-59` 執行，2026-08-26。
> 目的：Demo 當天可能站著、戴著裝置、手不方便一直點畫面——檢查整個面板
> 能不能只用鍵盤走完。
> 測法：headless Chrome + CDP 的 `Input.dispatchKeyEvent`（真的鍵盤事件，
> 不是 JS 合成的 `dispatchEvent`），對每個模式送真的 `Tab`，追蹤
> `document.activeElement` 的變化，量測 `outline` 是否可見。所有測試程序
> 都用明確 PID（`$!` 記下來）起停，這輪起沒有用任何 pattern-based kill
> （中途犯過一次這個錯誤，已回報並改正，見對話紀錄）。

## 結論摘要

| 項目 | 結果 |

## 1. `Tab` 可達性（五個模式）

**全部通過。** 每個模式從側邊欄開始，`Tab` 18 次都能走過側邊欄五個
nav item、狀態摘要、投影模式/摺疊按鈕，再進入該模式的所有互動元素
（按鈕、輸入框、下拉選單、`range` 滑桿），最後自然循環回到第一個
nav item（測試工具一開始把這個「循環回起點」誤判成「焦點跑丟」，
後來確認資料是**每輪循環結束都正確回到 `監測1`**，不是真的丟失）。

各模式 `Tab` 走過的可互動元素數量（跟該模式畫面上看得到的控制項數量吻合，
沒有元素被跳過或不可達）：`monitor` 11 個、`record`（表單畫面）14 個、
`quiz` 16 個、`validate` 12 個、`replay` 5 個。

## 2. 🔴 → ✅ 焦點可見度

**修前**：全站只有兩條孤立的 `:focus`/`:focus-within` 規則（都在
`record.css`，各管一個輸入框跟一個清單項目），**其餘所有東西**（五個模式
的每一個 nav item、按鈕、切換開關）**完全沒有明確焦點樣式**，全靠瀏覽器
自己的預設外框——這在深色主題、投影機對比度更差的情況下，很可能看不清楚。

**已修**：在 `tokens.css` 加一條全域 `:focus-visible { outline: 3px solid
var(--accent); outline-offset: 2px; }`（琥珀色，跟其他「這是被選中/強調」
的視覺語言一致）。用 `:focus-visible` 不用 `:focus`——只在鍵盤導覽時出現，
滑鼠點擊不會每次都閃一下外框。

**測過**：五個模式的 `Tab` 序列裡，幾乎每一步 `outlineStyle: solid,
outlineWidth: 3px, outlineColor: rgb(232, 163, 61)`，全部一致。

**兩個例外，處理方式不同**：

1. **`record` 的文字輸入框**（受試者代號、模式、距離等）：`record.css`
   既有規則 `input:focus { outline: none; border-color: var(--accent); }`
   蓋掉了新的全域樣式，改用邊框變色代替外框。**這是合理的既有選擇**（文字框
   本來就有邊框，變色比再加一圈外框更乾淨），邊框變色本身仍然清楚可見，
   沒有修改。
2. **`quiz` 的融合權重滑桿**（`C17` 的 `w` 滑桿，Demo 核心元件之一）：
   `quiz.css` 原本寫 `.quiz-w-slider { outline: none; }`**卻沒有補上任何
   替代樣式**——鍵盤 `Tab` 到這顆滑桿時完全沒有任何視覺提示，是稽核中
   找到的真實缺口。**已修**：滑桿是自訂樣式（`appearance:none`），瀏覽器
   預設外框在自訂滑桿上會框住整條軌道（不好看），所以改成業界標準做法——
   在 `::-webkit-slider-thumb`/`::-moz-range-thumb` 上用 `:focus-visible`
   加 `box-shadow` 光暈，聚焦時滑桿把手周圍會出現雙層光暈（`--bg` 內圈 +
   `--accent` 外圈）。

## 3. `Tab` 順序

**通過。** 沒有觀察到 DOM 順序跟視覺順序不一致導致的亂跳——側邊欄
（上到下）→ 主要內容區（大致由上到下、由左到右）是每個模式一致的模式。

## 4. ⚠️ 模式切換後焦點去哪

**確認可靠的部分**：全域數字鍵（`1`–`5`）切換模式**穩定可用**——按
`3` 直接把 `active_mode` 切成 `quiz`，這條走的是 `shell.js` 自己的
`document.keydown` 監聽，不依賴瀏覽器對按鈕的預設鍵盤動作，測試工具送出的
合成鍵盤事件跟這條路徑相容，重複測過都準確。

**沒能確認的部分**：用 `Tab` 移到某個 nav item 之後，用真的 `Enter`/
`Space` 鍵**啟用**該按鈕（模擬使用者鍵盤操作一個聚焦中的按鈕，而不是
用數字鍵快捷鍵）——這條路徑在 CDP 合成鍵盤事件下**沒有觸發模式切換**。

**這比較可能是測試工具的限制，不是真的 bug**：`nav item` 全部是原生
`<button>` 元素（不是套了 `onclick` 的 `<div>`），HTML 規格保證任何瀏覽器
對「聚焦中的 `<button>` 按 Enter/Space」都會觸發 `click`，**不需要 app
自己寫任何 JS**——這是瀏覽器原生行為，CDP 的合成鍵盤事件對「瀏覽器預設
動作」的還原度眾所周知不是 100%。**沒有假裝這條驗過**：建議找真人在真的
瀏覽器裡按一次 `Tab` + `Enter` 切換模式確認，但不認為這是 app 本身的
缺陷（`shell.js` 沒有動任何跟這個相關的邏輯）。

## 5. ⚠️ `record` 核心動作（開始錄一筆／確認／丟棄）能否純鍵盤完成

**這是你點名最重要的一項，也是唯一沒有跑通即時驗證的一項——誠實說明。**

**程式碼審查（`record.js` 的 `onTrialKeydown`/`onTrialKeyup`，沒有修改，
只讀）**：實作完整、合理——

- **`Space`**（按住開始錄、放開結束）：`keydown` 觸發 `triggerHoldStart()`，
  `keyup` 觸發 `triggerHoldStop()`，且 `CONFIRM` 狀態下 `Space` 不會誤觸發
  新的錄音（明確排除）。有 `e.preventDefault()`（避免按空白鍵捲動頁面）。
- **`Enter`**（`CONFIRM` 狀態下確認保留）：呼叫 `triggerConfirmKeep()`，
  只在 `CONFIRM` 狀態生效，不會在其他狀態誤觸發。
- **`Escape`**：`CONFIRM` 狀態下丟棄（`triggerConfirmDiscard()`），其他
  狀態中止當前錄音（`triggerAbort()`）——邏輯一致（「Esc 都是不要這個」）。
- **`R`**：`IDLE`/`REST` 狀態下重錄上一筆已存檔的（C14），
  其他狀態重錄目前這筆未存檔的——程式碼註解裡誠實記錄這是**這個 story
  自己的選擇**（不在 C12.md 原始「包含」清單裡，是因應 `esp-mask-test-ad`
  當初「abort 與 redo 都要能到達且可分辨」的要求後加的）。
- 這些監聽都掛在 `document` 層級、有 `isRecordTrialScreenActive()` 守衛
  （只在真的在錄音畫面時生效）、有 `isTypingTarget` 檢查（雖然這個畫面
  本來就沒有文字輸入框，註解說明是為了跟 `C02` 的規矩保持一致）、
  排除 `Ctrl/Alt/Meta` 組合鍵——**看不出設計上的缺陷**。

**為什麼沒有即時驗證**：要驗證這幾個鍵，畫面必須真的進入「錄音中」畫面
（`record.js` 內部的 `screen === "trial"`，不是只切 DOM class 就能騙過去，
之前斷線稽核用過的「直接改 DOM display」那招在這裡行不通）。要走到那個
畫面需要走完整個真流程：填表單 → `POST /session/start` → 進入 baseline
畫面 → **真的等 30 秒**的 baseline 擷取（畫面上的倒數是本地估計，程式碼
自己的註解寫著「尚未收到伺服器的即時基線進度事件」）→ 才會自動進入
trial 畫面。我在時限內跑了三次，都卡在 baseline 畫面沒能等到自動前進
（可能需要比我等的更久，或者這條路徑本身有東西沒接上——**不確定，
沒有足夠證據下結論**）。

**沒有假裝驗過**：這一項標記為需要人工驗證——**找一台真的裝置或真的
mock，走完整個 30 秒 baseline，再實際用 `Space`/`Enter`/`Esc` 操作一次**。
我對程式碼本身有信心（讀起來設計得很仔細），但沒有現場按過鍵盤看它動。
