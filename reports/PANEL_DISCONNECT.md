## 1. 全域連線狀態（`shell.js`，C04）

**通過。** `main.js` 的 `EventSource.onerror` 正確呼叫 `notifySseConnection(false)`，側邊欄連線文字從「已連線 proto2 ...」變成「**斷線（主機）**」，`class` 正確套用 `.status-conn-text.down`（紅色，`--status-bad`）。

**bridge 重啟後**（沒有重新整理頁面）：`EventSource` 原生自動重連，`onopen` 觸發 `notifySseConnection(true)`，文字自動變回「已連線」，`monitor` 的 Hz 讀數在原生重連後立刻恢復即時更新。全程 console 只有 `[panel] SSE connection error`/`[panel] SSE connected` 這兩種 `console.log`（不是 error），**沒有任何未捕捉例外**。

**唯一的觀察**：整個側邊欄的「紅色外圈警示」（`.sidebar.status-alert`，C04 的最高強度警示）**沒有**在 SSE 斷線時觸發——那個外圈只綁定 `drop_rate`/`symmetry` 兩個品質指標的紅燈，不含 SSE 連線狀態本身。純 SSE 斷線只有側邊欄一小行文字變色。**這是否夠醒目，值得你判斷**——文字變色沒有其他模式的內容那麼顯眼，尤其在投影機上。我沒有動它（`.sidebar.status-alert` 的觸發條件屬於 C04 既有邏輯，不確定改動範圍是否超出這輪授權，回報給你）。

**顏色判斷**：我沒有把「斷線（主機）」的紅色改成琥珀。理由：這不是「功能還沒接上」（`.pending-note` 那種可预期、不緊急的狀態），而是「本來連著、現在真的斷了」——瀏覽器完全連不到 bridge，是這個 app 能發生的最嚴重狀態之一，跟「低品質、但仍在運作」的語意不同。維持紅色。

## 2. `monitor`：🔴 畫面凍結但看起來像活的（最糟的失效方式）

**這正是你點名最擔心的失效模式，而且真的發生了。**

斷線後 3 秒，側邊欄摘要的 Hz 正確降到 `0.0 Hz`。**但同一時間，`monitor` 內容區塊裡每個感測器面板自己的 Hz 標籤（`Sensor A · 距離 ... 30.0 Hz`）完全沒有變化**——我等到 **18 秒**，那個數字仍然停在斷線前最後一次收到的 `30.0 Hz`，一秒都沒有動過。熱力圖格子（`17 17 17 17...`）同理，是靠同一條 `onData` 更新的，斷線後就是最後一幀，不會再變。

**結果**：畫面正中央的內容（感測器面板、熱力圖）在斷線期間看起來**完全正常、跟連線時一模一樣**，唯一的差異只有左上角一行小字（「斷線（主機）」）。投影機上、觀眾距離螢幕有一段距離時，這行小字很容易被忽略——這正是你說的「一張不動的漂亮畫面，跟一張正在更新的漂亮畫面，長得一模一樣」。

**根因（推測，沒有動手改）**：這幾個 Hz 標籤跟熱力圖格子顯然是**只在收到新的 `tof` 事件時才重繪**，沒有獨立的逾時/心跳機制在沒有新資料時把自己重置成「--」或加上視覺標記。`C09` 的 quality 面板反而是對的（`quality-level-dot.level-unknown` 有專門的「未知」空心圈樣式）——`monitor.js` 主要的熱力圖/Hz 顯示沒有套用同一套邏輯。

**不是我能改的**（`monitor.js` 這輪歸 `7c`，且它正在改）——回報給你判斷要不要排修。

## 3. `record`：🔴 錄製途中斷線，那筆 trial 卡死不會逾時（你點名最重要的一項）

**用真事件模擬「正在念到一半，線鬆了」**：透過 `bus.js` 送 `PROMPT → COUNTDOWN → CAPTURE`（不送 `SAVE`，因為斷線後裝置端本來就不會再送任何東西），然後砍掉 bridge。

**結果**：`.trial-card` 的 class 停在 `trial-card state-capture`，`.trial-state-label` 停在「**錄製中**」，**整整 28 秒都沒有任何變化**。`state-capture` 的紅色邊框自帶 CSS `@keyframes trial-capture-pulse` 呼吸動畫——**這個動畫是純 CSS，不需要資料就會一直跑**，所以卡片視覺上持續在「脈動」，看起來像正常錄製中，而不是卡住。

**對使用者的實際影響**：如果 `E05` 真的在念一個詞的當下斷線，畫面會停在紅色脈動的「錄製中」，**沒有逾時、沒有錯誤訊息、沒有任何提示告訴使用者「這筆錄不到了」**。使用者唯一能發現異狀的方式是抬頭看左上角那行「斷線（主機）」小字。這筆 trial 的命運（有沒有存檔、要不要重錄）完全不透明。

**不是我能改的**（`record.js` 歸 `4f`，即使它目前沒在改也不能碰）——回報給你，這是我認為優先度最高的一個發現，直接關係到 `E05` 蒐集主資料集當天的真實風險。

## 4. `quiz` / `validate` / `replay`：沒有觀察到問題

三個模式在斷線期間切換過去、console 全程乾淨，沒有未捕捉例外。這三個模式本來就沒有「持續自我更新的即時讀數」（不像 `monitor` 的熱力圖），主要靠按鈕觸發（「觸發辨識」「執行 A/B/C/E」等），斷線後使用者點按鈕會走既有的「尚未串接」/`.pending-note` 降級路徑（本來就測過），不會不明不白地卡住或報錯。

**`validate`/`replay` 的後端端點**（`ed`、`7c[c32fd9]` 正在接）目前多數還是 404，這輪測到的「沒問題」只代表「斷線沒有讓它們變得更糟」，不代表功能完整——這是已知、正在進行中的狀態，不是這輪的新發現。
