## Q1 🔴 `GET /replay/sessions`：後端回對了，前端顯示不出來

**直接呼叫後端**：
```json
[{"file": "2026-08-26_replaytest.h5", "path": "...", "bytes": 19312, "modified_at": "..."}]
```
是一個**陣列**，每個元素是物件。

**但 `replay.js` 檔案開頭自己寫的契約註解**（line 12）：
```
GET  /replay/sessions  -> {"files": ["<name>", ...]}
```
**期待一個帶 `files` 鍵的物件**，裡面是純字串陣列。

**實際程式碼**（line 71）：
```js
const files = Array.isArray(data.files) ? data.files : [];
```
真實回應是陣列，`data.files` 是 `undefined`，`Array.isArray(undefined)` 是
`false`，**`files` 靜靜地變成空陣列**——不是抓不到端點的那個 catch 分支
（`res.ok` 是真的、`res.json()` 也真的成功），**是解析對了 JSON、
只是形狀不對，完全不會報錯**，下拉選單只剩「— 選擇 session —」這個
預設選項。**這就是你要我們找的第五個案例。**

## Q2 選一個、按播放：用手動輸入路徑繞過 Q1 之後——

**先用 `schema_example.py` 造的空白 session 測**，`POST /replay/start`
回 `400 {"error": "... 從 trial_idx=0 開始沒有任何可重播的事件"}`——
**這個是對的**，因為那個檔案本來就是空的示範 schema，不是 bug。

**改用真實 session（`sessions/2026-08-26_S01.h5`，900 幀）後**，
`POST /replay/start` 回 `200`、`n_events: 2104`，畫面正確顯示
「回放中：...」、時間軸出現 1 個 trial 標記。**確認會動。**

🔴 **但過程中意外抓到第二個獨立的落後案例**：`replay.js` 對 `/replay/start`
的錯誤處理（line 159-163）——**不管後端回什麼狀態碼**（404 端點真的不存在、
還是 400 這種端點存在但這次請求有問題），**一律顯示同一句「尚未串接
（/replay/start 還沒上線）— 已知：B17 後端邏輯完成，等 ed 接上」**，
真正的錯誤內容（例如「這個 session 沒有可回放的事件」）**只寫進
`console.warn`，不顯示給使用者**。現在 `ed` 已經把端點接上了，**這句
「還沒上線」的訊息本身變成過時、會誤導人的**——使用者選了一個真的有問題
的 session（例如檔案損毀、路徑打錯），畫面只會說「還沒接上」，看起來像
是這個功能整個沒做，而不是「你選的這個檔案有問題，原因是 XXX」。

## Q3 播放控制：暫停/單步/變速/跳轉

用真實 session 測過：
- **暫停**：點擊後按鈕文字正確從「⏸ 暫停」變成「▶ 播放」，切換正常。
- **單步**：按鈕存在、點擊沒有拋出例外，沒有更進一步驗證單步後時間軸/畫面
  的精確變化（900 幀的單一 trial，單步的視覺效果不明顯，沒能肉眼確認）。
- **變速（0.25×/1×/4×）**：三顆按鈕都在、點擊沒有例外。⚠️ **沒能確認
  點擊後是否有「目前選中」的視覺高亮**——我的測試在點擊當下立刻讀
  `className`，可能量到事件處理器還沒跑完的中間狀態，不確定是真的沒有
  高亮還是我測試的時間點抓錯，**沒有把不確定的東西講成確定的**，建議
  真人點一次肉眼確認。
- **跳轉（輸入 trial 編號 + 按跳轉）**：點擊沒有拋出例外，因為這個 session
  只有 1 個 trial，沒能測到「跳到第 5 筆真的跳過去」這種多筆情境。

全程 **console 完全乾淨**，沒有任何未捕捉例外。

## Q4 ✅ 「這是回放不是即時」——做得比預期好，三層信號同時存在

截圖確認，回放中同時看得到：

1. **側邊欄連線狀態文字**變成「● ▶ REPLAY」（琥珀色，`C04` 既有邏輯）
2. **右上角浮水印**「▶ REPLAY」——**切到 `monitor` 模式後浮水印依然可見**
   （`opacity` 從 `replay.js` 自己切到 `monitor` 前後都量到 `1`），
   證明 C24.md「不能只在回放模式裡標」這條真的做到了。
3. **意外的第三層**：`monitor` 模式在回放期間顯示一個紅色警示條
   「⚠ 資料已停止 —— 畫面停在斷線前最後收到的值，不是即時資料」——
   這看起來是 `monitor.js` 最近才加的新東西（**可能是回應我上一輪
   `PANEL_DISCONNECT.md` 那個「凍結但看起來像活的」發現而加的**），
   雖然文字寫的是「斷線前」不是「回放中」，用詞跟這個情境不完全貼合，
   但**效果是對的**——明確告訴使用者眼前的數字不是即時的。這個文字用詞
   要不要因應回放情境調整，是 `monitor.js` owner 的判斷，回報但沒有動手
   （不是我的檔案）。

**這題原本最擔心的失效模式（凍結但看起來像活的）在這裡沒有發生**——
至少有三個獨立信號會提醒使用者。

## Q5 ⚠️ 回放結束後回不回得去即時模式

**沒有找到明確的「停止回放」/「離開回放」按鈕**——控制列只有「載入並播放」
「播放/暫停」「單步」「變速」「跳轉」，沒有第七顆「停止」。

**但浮水印會自己消失**：`REPLAY_WATERMARK_LINGER_MS = 3000`（`replay.js`
檔案開頭常數），配合 `shell.js` 既有的 `REPLAY_WINDOW_MS`——**沒有新的
`replay:true` 事件進來 3 秒後，浮水印自然淡出**，不需要手動按停止。
這個機制測到了（截圖裡最後一次檢查 `opacity` 變回 `0`）。

⚠️ **沒能確認的是後端層面**：浮水印消失只代表「畫面不再顯示回放中」，
不代表「後端真的停止回放、恢復把真實裝置資料往外送」——這個需要看
`bridge_server.py` 的回放狀態機（不是我這輪能動的檔案），**如果回放
還在背景繼續跑（例如使用者中途切走，沒等它自然播完），使用者會不會真的
看不到新的即時資料**，這個問題留給你判斷要不要追下去。

## Q6 ✅ `replay:true` 前端有在用

不只查了一個欄位——這輪至少看到兩處獨立消費 `replay` 相關資訊的地方：
`shell.js` 的 `notifyGlobalStatus`（驅動側邊欄「▶ REPLAY」文字跟顏色）、
`replay.js` 自己的浮水印邏輯。兩處都在稽核中觀察到正確反應，**不是只有
其中一處在讀，另一處沒接上**。
