## 1. 現在是什麼狀態

### 1.1 軟體能做什麼

| 你可以做的事 | 怎麼做 |
|---|---|
| 接上板子看即時畫面 | 啟動 bridge + 開瀏覽器面板（監測／錄製／測驗／驗證／重播五個模式） |
| 錄一個 session 到檔案 | 面板的「錄製」模式；資料存成 HDF5，含時間戳、baseline、品質標記 |
| 自動切出「詞從哪開始到哪結束」 | 音訊 VAD（聽聲音）與 ToF VAD（看嘴型）兩套，兩者共用同一個偵測器 |

| 認出你說的是哪個詞 | 詞彙集八個詞（八／五／一／啊／四／好／停／不要）+ 拒識 |
| 沒接板子也能開發／示範 | 假裝置（`ssi-backlog/tools/mock_device.py`）會產生逼真的訊號 |

### 1.2 ⚠️ 所有結論都是合成資料，一個真數字都沒有

**這是這份文件最重要的一句話。**

`reports/` 底下每一份實驗報告的開頭都有這行警告，不是客套：

> ⚠️ 本報告使用合成資料，數字不是真實結論。

合成資料是我們**自己設定可分性**的假訊號。它能驗證「程式算得對不對」，
**不能**回答「這個裝置到底行不行」。真實資料可能比合成的更難分——
那時候需要的樣板數只會更多，準確率只會更低。

驗證報告產生器（`analysis/run_all.py`）**預設就把報告標成合成**，
要加 `--real` 才會拿掉那個警告。這是刻意的：**忘記加旗標的人不該產出
一份看起來像真實結論的報告。**

## 2. 你要做什麼才能拿到真實結果

### 步驟

1. **先讀 [`E01_bringup_checklist.md`](E01_bringup_checklist.md)。**
   那份清單是上機的**唯一事實來源**，包含每一項要量什麼、怎麼量、
   量完填回哪個檔案。**本文件不重複它的內容。**

2. **照那份清單的第 1 節先做「阻擋決策的量測」。**
   那幾項會改變後續工作的方向——先做它們，不要照順序做。

3. **第 2 節的三個未驗證假設，一次全部確認掉。**
   每一個都只要幾分鐘，但錯了會讓後面所有分析的方向反掉（見第 4 節）。

4. **開始蒐集資料**（`E02` → `E05`）。清單第 6 節「錄製時要記得的事」
   是錄壞了就得重錄的那些細節，錄之前看一遍。

5. 🔴 **跑驗證報告，主線是面板的「驗證」模式（`validate`）**：填入
   session 路徑，勾選 `real`（真實資料才勾，不勾預設當合成資料處理），
   按「▶ 執行 A / B / C / E」。完整操作與五張卡片各自在問什麼問題，見
   [`DEMO_RUNBOOK.md`](DEMO_RUNBOOK.md)。命令列版本一樣可用（`validate`
   模式背後就是呼叫這支）：
   ```bash
   python -m analysis.run_all --session <你的檔案.h5> --real
   ```
   多次戴脫的資料要給多個檔案：`--session a.h5 --session b.h5`。
   正式報告請加 `--ablation-permutations 1000`（預設 200 是為了跑得快）。

6. **看通過矩陣。** 那張表是你每天最常看的東西，一眼掃完就知道哪一項
   掛了。失敗時上面會有紅色警示與診斷建議。⚠️ **`blocking`／
   `inconsistencies`／`limitations` 三個欄位是委員最可能追問的地方**
   ——後端一定會算，`validate` 前端如果還沒顯示出來，直接
   `curl http://<bridge>/verify/state` 讀 JSON，細節見 `DEMO_RUNBOOK.md`
   第 3 節。

### 報告會產出什麼

`summary.md`（通過矩陣置頂）、`summary.html`（可直接用瀏覽器開）、
各實驗自己的 md、以及 `figures/`（PNG 300dpi + PDF 向量圖各一份）。

⚠️ 報告裡有三種狀態，**意思完全不同**：

## 3. 開發過程中發現的、會影響你決策的事

> 每一條都附出處。**數字以出處為準**，本節只講「這對你的決定有什麼影響」。

### 3.1 「多錄幾次樣板」救不了拒識——但校準方法換掉之後就好了

**這一條的實際結論跟直覺相反，值得花一分鐘看。**

[`D09_template_count_study.md`](D09_template_count_study.md) 的發現是：
**誤拒率在 n=10 到 n=100 之間幾乎不變**（ToF 一直卡在 32–35%）。
也就是「多錄樣板」不是解法，問題出在**校準方法本身**。

[`D22_reject_calibration.md`](D22_reject_calibration.md) 換掉校準方法
（單邊 LOO → 雙邊 ROC）之後，同樣的資料誤拒率降到接近 0。

**對你的影響**：
* 每個詞錄到 **30 筆左右**就夠了，再多幫助有限（D22 表格裡 n≥30 時誤拒率
  **≤1.1%**——n=40 實測是 1.1%／0.6%，不是精確的 0，但已經遠低於舊方法）。
* 新校準方法的耗時比舊的多約 18 倍，但仍遠低於預算——**除非**你之後把
  樣板數大幅加上去（耗時隨樣板數平方成長）。
* 舊方法的程式碼刻意保留著當對照，真實資料到手後要**兩個都跑一次**比較。

### 3.2 「詞」與「靜止」的錄製次數比例——新方法下影響很小

`D22` 掃過 1:0.3 到 1:3 五種比例：
**舊方法**受比例影響（誤拒率 28.9%→35.6%），**新方法幾乎不受影響**
（全部落在 0–1.1%）。

**對你的影響**：不必為了湊比例多錄「靜止」樣本。錄成大致 1:1 就好，
不用刻意配。

> ⚠️ 你可能會聽到「錄製次數必須對齊，不然誤拒率會從 7% 升到 15%」。
> **那組數字是真的量過的，但它是用舊的校準方法量的**，而且從來沒有進過
> 任何檔案（見 4.4）。`D22` 換掉方法之後這條建議已經過時——
> **以 `D22` 的實測表為準。**

### 3.3 監測畫面吃 CPU — 反應變順了，但**總 CPU 還沒達標**

這一條有兩個不同的數字，**很容易混在一起，混了就會做出錯的決定**：

| 指標 | 量的是什麼 | 現況 |
|---|---|---|
| 總 CPU（`/proc`） | 整個瀏覽器吃掉多少 CPU | **30.65%**（預算 15%），[`PANEL_INTEGRATION.md`](PANEL_INTEGRATION.md) §5 |
| 主執行緒 `TaskDuration` | 畫面**卡不卡**、會不會掉幀 | **55.9% → 21.7%**，[`C_monitor_perf.md`](C_monitor_perf.md) |

[`C_monitor_perf.md`](C_monitor_perf.md) 找到並修掉了根因（PCA 軌跡圖每幀
讀取元素尺寸，逼出同步 layout）。**主執行緒忙碌時間降了約六成，畫面明顯
變順。**

⚠️ **但那份報告自己說：`/proc` 量到的總 CPU 修復前後幾乎沒變。**
差別在於總 CPU 還包含 GPU／raster 執行緒的軟體合成成本，那部分沒被這次
修復影響。**所以「30.65% 超標兩倍」這件事目前仍然成立**，那份報告建議
在乾淨的機器上（沒有其他 agent 搶 CPU）重量一次才能下結論。

**對你的影響**：
* **Demo 排練（`E07`）時仍然建議停在測驗模式**，不要停在監測模式。
* 其餘三個模式（測驗／錄製／重播）都在 11–13%，**都合格**。
* 如果你想確認總 CPU 到底修好了沒，**在一台沒有其他東西在跑的機器上重量一次**。

### 3.4 舌音量不到 — 這是可以寫進論文的誠實限制

詞彙集（`config/vocab.json`）的八個詞涵蓋 A 雙唇／B 圓唇／C 展唇／
D 開口／F 擦音／G 應用六類，**沒有任何 /t,d,k/ 的舌音詞**。

**對你的影響**：viseme 敏感度熱力圖的「舌音」那一列**永遠是空的**。
這不是量測失敗，是詞彙集的設計取捨——「本系統的詞彙集不涵蓋舌音，
因此無法驗證該類別」本身就是一句可以寫進論文的限制陳述。

要改的話會連動測驗版面、樣板數、錄音量，成本不小。**目前決定不改。**

### 3.5 串擾實驗需要「兩次不同的錄製」才跑得起來

`C0` 串擾實驗要比較「只開一顆感測器」與「兩顆都開」的差異——那是
**兩種不同的擷取組態**，一個 session 檔給不了。

**對你的影響**：`E02` 錄的時候要**在同一次戴上分段錄**：

| 錄什麼 | 指令 | 量到的是 |
|---|---|---|
| 只開 A | `SENS:B=0` | 「B 開著會不會干擾 A」 |
| 只開 B | `SENS:A=0` | 「A 開著會不會干擾 B」 |
| 兩顆都開 | 兩顆都開 | 上面兩個的對照組 |

🔴 **三段必須是同一次戴上（同一個 `wear_id`）。** 中途拿下來重戴的話，
**戴法差異會被算成串擾**——串擾的門檻只有 2 mm，而重戴一次造成的距離差
輕易就超過它，而且**結果看起來完全正常，只是數字偏大**。

驗證報告會自動從 `/meta` 的 `sensors_enabled` 配對這三段。只錄了其中一個
方向時，矩陣的「實測」欄會直接寫成 `A: 1.30 mm（B 未量測）`——
**覆蓋率會出現在你會掃的那一欄，不會藏在別的地方。**

⚠️ **兩個限制**：
* `sensors_enabled` 記的是**主機端送出去的指令**，不是裝置回報的狀態
  （韌體沒有回報這個）。**指令送出去不等於裝置照做了**，報告會標註這件事。
* 建議**同時開 ambient**（`AMB:1`）。`D10` 明訂 `ambient_per_spad` 是串擾
  **最靈敏**的指標——只看距離差可能漏掉「還沒到 2 mm、但 ambient 已經明顯
  上升」的干擾。沒有 ambient 資料時報告會提醒。

### 3.6 兩個 VAD 用同一個偵測器，這是刻意的

「嘴巴比聲音早動多久」是把兩個 VAD 的起點相減。如果兩邊的演算法有任何
一點不同，**那個差值裡就混進了程式差異，而它看起來會跟研究發現一模一樣**。

所以兩者共用同一份偵測核心，門檻倍數也刻意相同，而且程式會**自動反推**
兩邊實際用的門檻，不一致就把那筆標成「不可比」。

**對你的影響**：
⚠️ **單筆的先行量沒有意義。** 兩個模態的時間量化誤差合起來約 ±46 ms，
而預期的先行量是 50–150 ms——同一個量級。**20 筆平均之後**誤差降到
約 ±10 ms，那時才站得住。報告裡的「正負號一致性」比平均值本身更有說服力。

### 3.7 訓練與推論兩條特徵組裝路徑本來不一樣，現在統一了——但舊報告的數字沒有跟著變

`analysis/run_all.py`（離線分析用的路徑）跟 `host/features/live_pipeline.py`
（即時推論唯一可能走的路）本來用兩套不同的邏輯處理「ToF 幀率 30Hz、
Mel 幀率 62.5Hz，兩者對不齊」這件事：前者用幀數截斷（第 i 個 ToF 幀配
第 i 個 Mel 幀），後者用 `Aligner` 按真實時間戳對齊。合成資料上量到
Mel 單獨看的距離可以差到 0.86–1.46（cosine 值域 0–2），甚至真的讓分類
結果翻轉過——但只看合併後的向量完全看不出來（ToF 通道權重夠大，把
問題稀釋掉了）。詳見 [`ALIGNMENT_MISMATCH.md`](ALIGNMENT_MISMATCH.md)。

✅ **已經修好**：`run_all.py` 現在改成呼叫同一份 `Aligner`／
`live_pipeline` 程式碼，兩條路徑不可能再走岔。

**對你的影響**：
🔴 **`D06`/`D08`/`D09`/`D22` 這幾份報告的數字是用修好前的離線截斷邏輯
算出來的**。`E05` 真實資料到手後用修好後的 `run_all.py` 重新分析，數字
很可能會跟這幾份舊報告不同——**這不是新的錯誤，是方法修正後的正常
結果**，但如果你直接拿舊報告的百分比去回答委員的問題，那些數字現在
已經不能保證代表現行系統。

### 3.8 錄音「按住多久」會變成特徵的一部分——已經在修，錄製時仍要注意

同一個詞只是按鍵按住的時長不同（0.5s vs 4.0s），算出來的距離可以跟
**兩個完全不同的詞**一樣遠。機制不是訊號被稀釋，是「講話動作」被重
採樣到固定 24 幀的**哪一格**隨錄音長度系統性偏移。詳見
`ALIGNMENT_MISMATCH.md`「按住多久會不會洩漏進特徵向量」一節。

✅ **`live_pipeline.py` 已經加了可選的 VAD 裁切**（`speech_window` 參數，
不給就是舊行為，向後相容）——這是長期的修法，把「真的在講話」的那段
先切出來再重採樣，理論上能解掉這個問題，但**這輪還沒有真實資料驗證
效果**。

**對你的影響**：🔴 **錄製時仍然要把每一筆的按住時長盡量控制得一致**
（見 `E01_bringup_checklist.md` §6），**不要假設 VAD 裁切上線就不用管
這件事**——上線是一回事，真實資料上效果如何是另一回事，兩者都要顧。
🔴 **同一個詞不要混用固定 2 秒視窗與 hold-to-record 兩種錄製模式**，
混用會人為放大這個落差。

### 3.9 ToF 與 Mel 兩個模態的距離尺度差約 5.18 倍——加了 euclidean 選項，但預設沒有換

使用者問過「不用歐式距離不行嗎」——已經加了這個選項
（`analysis/similarity/euclidean_baseline.py`，`dist_method="euclidean"`
現在可用），**但預設值沒有改，還是 `cosine`**，理由如下。

用真實 production 路徑（`SessionWriter`→`load_session`→
`build_templates_from_session`）量測發現：**ToF 通道的歐式距離比 Mel
通道大約 5.18 倍**（結構性原因：D01 的 ToF z-score 強制單位變異數，
D02 的 Mel 預設只做 CMN、沒有除以標準差；兩者維度也不同）。分類準確率
兩種距離打平（融合時 `fusion.py` 會先各自正規化，尺度差不影響分類），
**但拒識正確率被腰斬**（`_reject` 正確攔下的比例從 66.7% 掉到
33.3%）——`reject_fused(w)` 用的是未正規化的原始距離加權相加，尺度差
5.18 倍讓融合結果幾乎被 ToF 主導。詳見
[`DISTANCE_COMPARISON.md`](DISTANCE_COMPARISON.md)。

**對你的影響**：**維持 cosine 預設**，除非你有其他理由想換
euclidean——換的代價是拒識明顯變不可靠，除非額外做跨模態尺度校正
（目前沒有做，需要另外設計）。

### 3.10 真板子上線後，schema 多了三個欄位幫忙診斷「資料到底完不完整」

真板子第一次上線就發現：`sensors_enabled`（指令設了什麼）不等於
**裝置真的有沒有送資料**。新增三個選填欄位（`ssi-backlog/CONTRACTS.md`
2026-08-26 的變更紀錄）：

- **`sensors_seen`**（`/meta` 與 `/trial_NNN` 各一份，值域相同、涵蓋範圍
  不同）：實際線上出現過哪些感測器的資料流，不是主機下的指令。`/meta`
  只到 baseline 為止，`/trial_NNN` 是那一筆錄製期間——**兩者不一致就是
  中途掉線的直接證據**，`E05` 事後可以靠這個分辨哪些 trial 完整、哪些
  只有半邊臉。`""` 是合法值（監測過整個 session 確實沒資料），跟「欄位
  不存在」（舊檔、沒量過）意義相反，不能互換。
- **`baseline_age_s`**（`/trial_NNN`）：這筆錄的當下，baseline 已經是
  幾秒前的。`record.js` 原本沒有 baseline 過期偵測（`monitor.js` 有 10
  分鐘門檻，`record.js` 沒有），`E05` 要連續錄 4 小時，中途過期幾乎必然
  發生——這個欄位讓事後從 HDF5 就看得出哪些筆是過期後錄的，不用只靠
  當下操作者有沒有注意到畫面警告。
- **串流逾時偵測**（`host/quality/metrics.py` 的 `stale_streams()`）：
  每條串流（ToF-A/ToF-B/Mel/mic）各自的靜默門檻，超過就標記成
  stale，餵進 `quality` 事件的警示。

**對你的影響**：這三個都是選填欄位，`E05` 錄製時**不需要你做任何額外
操作**，它們是給事後分析用的診斷資訊，出現不一致或 `sensors_seen`
缺 A/B 時代表那段資料可能只有半邊，分析時要能篩得出來，不要當成完整
資料處理。

## 4. 已知的技術債與未驗證的假設

### 4.1 🔴 zone 佈局是未驗證的假設 — **錯了建議會反向**

全鏈路假設感測器的 16 個格子是 row-major（`zone i → (i//4, i%4)`）。
**ST 的官方標頭沒有文件化這件事。** 程式與圖上都標了
`ASSUMED, unverified`。

**為什麼這條排第一**：`D11` 的產出是「感測器該往哪個方向調」。
**佈局假設錯了，熱力圖會翻轉，那個建議就是反的**——而你會照著它調，
然後越調越差，全程沒有任何錯誤訊息。

**驗證方法在 [`E01_bringup_checklist.md`](E01_bringup_checklist.md) 第 2.1 節，
遮住感測器一個角落看哪一格變化，一次就能確認。**

### 4.2 `ToF_L` / `ToF_R` 對應哪一顆，未確認

目前假設 L=A、R=B。驗證方法（第 2.2 節）：`SENS:B=0` 之後用手機相機
看哪一顆的紅外光熄滅。

數學上兩者對稱，**標反了不影響任何分數**，只影響報告的文字說明指向
哪一顆實體感測器。

### 4.3 `$H` 之後是否真的緊跟 `$STATUS`，未上機確認

PING 校時靠「後面緊跟 `$STATUS` 的那個 `$H`」來分辨「PING 回覆」與
「1 Hz 週期心跳」——**兩者長得一模一樣**。認錯會量到假的最小往返時間，
而那個假值看起來還特別「好」。

韌體端回報順序是對的，但沒有在真機上驗過。上機時看一眼校時結果的
`confirmed` 旗標即可。

### 4.4 🔴 有一部分結論**只存在於開發過程的對話裡，沒有進 repo**

**這一條會影響你怎麼看待其他每一條。**

開發過程中，各個部分的量測與判斷是透過訊息回報給協調者的。多數重要結論
被寫進了 `reports/` 與 `ssi-backlog/CONTRACTS.md`，**但有漏網的**——
那些結論**只存在於當時的對話訊息中，讀 repo 的人看不到它們**。

**這是怎麼發現的**：寫這份交接文件時，我拿到一組數字（「錄製次數不對齊
會讓誤拒率從 7% 升到 15%」），去 `reports/` 與 `ssi-backlog/` 全庫查證，
**查不到出處**。後來確認那組數字確實量過，但它從頭到尾沒有進過任何檔案。

**為什麼這比那組數字本身重要**：一個只在對話裡的結論，會以「聽說」的形式
繼續流通，而且**沒有任何機制讓它被更新**。上面那組數字就是這樣——它是用
**舊的校準方法**量的，而 [`D22_reject_calibration.md`](D22_reject_calibration.md)
換掉方法之後結論已經翻轉（見 3.2），但「要對齊次數」這個說法還在流傳。

**對你的影響**：

> ⚠️ **若你在任何地方（包括口頭轉述）遇到一個查不到出處的數字，
> 以 [`reports/`](.) 與 `ssi-backlog/CONTRACTS.md` 的實測表為準。**
> 那兩個地方的數字有版本、有變更紀錄、會被後續發現更新；
> 對話裡的數字不會。

**如果你之後自己或找人繼續開發**：任何值得記住的量測，
**當下就寫進檔案**。寫在訊息裡等於沒寫。

## 6. 最後：兩個關於未來的自己的習慣

開發過程中反覆出現同一類問題：**程式完全正確，但結論是錯的，而且不會
有任何錯誤訊息。** 例如：

* 除以一個「小到沒有意義」的標準差 → 某個格子的數值爆到上萬，主宰整張圖
* 跨通道取最大值 → 純雜訊也會拿到 3.4，被判成「中等敏感」
* 交叉檢查讀錯一個欄位名 → 那一票永遠不存在，永遠不會發現矛盾
* 偵測不到時填 0 或填視窗邊界 → 看起來像「整段都在動」

**應對方式是把每一條約定都變成一個會叫的檢查**，而不是寫在文件裡靠人記得。
現在有一批這樣的守門員：圖上不准有中文、發散色階不標數值就擋、σ 下限、
「沒有資料」與「沒有問題」必須分開回報。

**你之後自己改程式或畫圖時，如果碰到「這件事要記得」，
請把它寫成一個會失敗的測試，不要寫成註解。**

（另一半是 4.4 那條：**值得記住的量測，當下就寫進檔案。寫在訊息裡等於沒寫。**）

### 但守門員也會過期 — 一條命名慣例

上面那個做法有一個副作用，這個專案已經踩到**至少三次**：

**測試把「當時做不到什麼」寫成了「正確行為」。** 限制解除的那天，
那條測試會變紅——而它紅了**是好事**，卻長得跟「你弄壞了東西」一模一樣。

三次的名字很說明問題：

| 舊名（在描述「現在做不到什麼」） | 改後（在描述「應該成立什麼」） |
|---|---|
| `..._is_always_skipped_from_a_session_file` | `..._when_there_is_nothing_to_pair` |
| `..._needs_at_least_two_opinions` | `..._is_reported_as_missing_data_not_as_agreement` |
| `..._at_session_start_counts_the_pre_roll` | `..._is_only_a_baseline_never_a_loss` |

**慣例**：斷言的是**當前限制**而不是**恆常性質**的測試，
名字裡放 `_currently_` 或 `_limitation_`，並在 docstring 第一行寫

> 這條斷言的是**限制**不是性質；限制解除時應該改寫，不是修程式讓它變綠。

這沒辦法自動偵測，但**它讓那種測試在 `grep` 裡看得見**——
而且改程式的人一眼就知道「這條紅了，先想想是不是限制被解掉了」。
