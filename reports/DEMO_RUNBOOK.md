## 0. 開場：這個研究要證明什麼

一句話：**「雙顆 ToF 感測器矩陣加上骨傳導麥克風，能不能分辨一個人無聲
說出的詞」**——不是「做一個能上線用的辨識產品」。`validate` 模式跑的
五項檢定，就是這句話的統計證據，不是一個 demo 產品的功能展示。

## 1. 裝置與資料怎麼來的

上台前務必先填好這幾個空白（現在寫不出來，因為還沒有人錄過真實資料）：

- 錄了幾個人、每人幾次戴脫
- 每個詞錄了幾筆（`E06` 的目標是每類 20–30 筆，見
  `reports/E01_bringup_checklist.md` §6.1）
- 錄製條件：正常/氣音/無聲、戴法幾何、環境噪音
- 使用的是哪一個 `templates/<subject>_<wear_id>.npz`、對應哪幾個
  session 檔（`analysis/similarity/build_templates_from_session.py`
  存檔時會一併寫一份 `.provenance.json`，記錄每個類別的樣板來自哪個
  session 的哪一筆——**這就是回答這題最直接的來源，不用自己重新翻**）

⚠️ **真板子今天實測發現 A 感測器會隨機掉線**（`reports
/E01_bringup_checklist.md` §0.5/§0.7）——**如果第一批錄音真的只有半邊
臉的資料，這裡要老實說「這批資料只有單邊 ToF」，不要含糊帶過**。
`validate` 模式的 `C0`（串擾）本身就是設計來檢查「兩顆有沒有互相干擾」
的，但它假設兩顆都在送資料；只有一顆有資料時，`C0` 該回報的是
`SKIPPED`（資料不足），不是誤判成 PASS 或 FAIL——上台前先確認一次
這裡顯示的是不是 `SKIPPED`，是的話要能解釋為什麼。

## 2. 🔴 驗證結果：五張卡片在問什麼問題

`validate` 模式一次跑 5 個實驗（`analysis/run_all.py` 的
`EXPERIMENT_META`），每一項都有自己的問題、判準、跟「這項掛了代表什麼」：

| 代號 | 名稱 | 在問什麼問題 | 判準 | 掛了代表什麼 |
|---|---|---|---|---|
| **C0** 🔴 必通過 | 串擾 | 兩顆 ToF 會不會互相干擾 | Δ_dist < 2mm | **硬體閘門**——兩顆互相干擾，下游 A/B/C/E 全部的數字都被污染，不是只有這一項不算 |
| **A** 🔴 必通過 | 逐 zone SNR | ToF 訊號有沒有真的進來 | SNR_L/SNR_R > 3 | **訊號閘門**——沒訊號就沒有什麼好分析的，`E03` 本來就把 SNR<3 當成「換戴法」的觸發條件 |
| **B** | 跨次戴 CV | 同一個人戴脫幾次，量到的東西穩不穩 | CV_between < 30% | 戴法流程需要改進——這是一個發現，不是「資料不可信」 |
| **C** 🔴 必通過 | Silhouette | **核心科學主張本身**：ToF 到底有沒有帶來可分辨的資訊 | Silhouette > 0.15 | 這項掛了，整個研究的主張站不住 |
| **E** | Viseme 敏感度 | 哪些音靠 ToF、哪些靠音訊（多模態互補的證據） | 擦音在 Mel 上明顯強於 ToF | 預期型態沒出現——是一個發現，不代表資料錯 |

**`MUST_PASS = ("C0", "A", "C")`**——這三項是刻意選出來的（不是 story
規定，是 `D15`/`analysis/reporting/verification_report.py` 自己的判斷，
理由寫在模組文件裡）：**這三項掛任何一項，整份報告的其餘數字都不能信**，
`B`/`E` 刻意不列入必通過，因為它們掛了是「發現」不是「資料污染」。

⚠️ **p 值**：`Silhouette`（C）本身的分數不會告訴你「這個分數是不是隨機
也能達到」——需要搭配 `D18` 的 permutation test（打亂標籤重跑，建立
null distribution）才能回答「真實分數跟隨機分數比起來顯著嗎」。上台前
確認一下這次的驗證報告有沒有帶 `D18` 的 p 值一起出來（`analysis/run_all
.py` 的 `--ablation-permutations` 引數控制置換次數，正式報告請明確指定
`1000`，預設 `200` 只是為了跑得快，`reports/HANDOFF.md` §4.5 已經記過
這件事）。

## 3. 🔴 誠實揭露——委員追問的第一個問題就在這裡

`analysis/reporting/verification_report.py` 的報告組裝會產出三個欄位：

- `blocking`：`MUST_PASS` 裡掛掉的項目（有的話，整份報告的數字都不能信）
- `inconsistencies`：跨實驗矛盾（例如 `C` 說有可分性、`E` 卻說某個型態
  沒出現——報告會把矛盾直接攤出來，不會各印各的讓人自己發現）
- `limitations`：系統層級、每次都成立的已知限制，目前固定包含：
  - **本報告全部數字來自合成資料，不是真實結論**（`E05` 之前恆真）
  - **舌音（viseme E）完全沒有涵蓋**——詞彙集 8 個詞沒有任何 /t,d,k/
    類的音，這一列永遠是空的，**不是量測失敗，是詞彙集設計取捨**
  - **zone 排列 row-major 仍是未驗證假設**——`D11`/`D14` 的所有空間
    結論在這個假設確認前，方向可能是反的（見
    `reports/ASSUMPTION_RISK.md`「假設 1」）

⚠️ **這三個欄位目前後端有算，但 `validate` 前端還沒有顯示出來**
（`ca` 剛發現，正在補——上台前先確認一次補完了沒）。**補完之前，
現場操作要自己去看這三個欄位**，不能只看畫面上的五張卡片：

```bash
curl -s http://<bridge-host>:<port>/verify/state | python3 -m json.tool
```

直接讀 JSON 裡的 `blocking`/`inconsistencies`/`limitations` 三個 key。
**這是委員最可能追問的地方——上台前自己先看過這三樣寫什麼，比較不會
被問到當場愣住。**

## 4. 現場操作

1. 開啟面板，切到「驗證」模式（`validate`，側欄第 4 個）。
2. 在輸入框填入樣板對應的 session 檔路徑（可能不只一個，同一次戴分開
   錄的都要填），視情況勾選 `fast`（降低計算量，數字會有出入，正式
   驗證不要勾）與 `real`（**標示這批是真實資料，不勾預設當合成資料**——
   `analysis/run_all.py` 的規則是「忘記加旗標的人不該產出一份看起來像
   真實結論的報告」，真的錄了真實資料要記得勾這個）。
3. 按「▶ 執行 A / B / C / E」。畫面會顯示執行中、耗時，完成後跳出通過
   矩陣（`真的實測過會回 202，之後輪詢 /verify/state`，不是假的 200，
   見 `reports/E01_bringup_checklist.md` §6.2 的驗證紀錄）。
4. **對照上面第 2 節的表逐項唸過去**，紅色警示（若有）優先講。
5. 講完矩陣，**主動**唸出第 3 節的 `limitations`（不用等委員問）——
   「本報告全部數字來自合成資料」這句話，自己先講比被問到才講更有
   可信度。

## 5. 已知限制與未來工作

- **`E01`–`E08` 全部尚未完成**，本報告目前只能用合成資料展示「驗證
  框架本身跑得動、判準設計合理」，不是真實結論。
- **A 感測器隨機掉線的根因還沒找到**（懷疑接線鬆動，見
  `reports/E01_bringup_checklist.md` §0.5），這會直接影響 `C0`（串擾）
  能不能真的跑，以及雙感測器互補的證據強不強。
- **訓練/推論兩條特徵組裝路徑曾經不一致，現在已修好**
  （`analysis/run_all.py` 已改成呼叫 `Aligner`／`live_pipeline` 同一套
  對齊邏輯，見 `reports/ALIGNMENT_MISMATCH.md`）——但 `D06`/`D08`/
  `D09`/`D22` 這幾份舊報告的數字是用修好前的邏輯算的，`E05` 之後重新
  分析可能會跟舊報告的數字不同，這不是新錯誤，是方法修正後的正常結果。
- **錄音時長會洩漏成特徵的一部分**（見
  `reports/E01_bringup_checklist.md`「每筆錄音的按住時長要盡量一致」），
  如果 `E06`/`E05` 錄製時沒有控制好時長一致性，樣板本身的品質可能受
  影響，這點如果被問到「怎麼確保樣板品質」時要能講出來。
- **舌音類別（viseme E）詞彙集完全沒有涵蓋**，這是設計取捨不是缺陷，
  上台前準備好這句話直接講，不要等委員發現才承認。
