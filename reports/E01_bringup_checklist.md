## 0.5 🔴 有一顆感測器完全沒資料（`fw=22bddce` 實測，正在發生）

**現象**：兩次觀察不一致，目前判斷是**其中一顆的實體連接不穩定**，不是固定
哪一顆壞掉，也不是軟體 bug：

- 第一次錄製：`$T,A` 約 30Hz 正常送、`$T,B` 0 行、`drop_A/B/M` 全 0
- 第二次（硬體 reset 後）的開機 log：`[Sensor A] is_alive failed
  (status=1 alive=0)`，`[Sensor B]` 卻成功 `ranging started`

**⚠️ 已排除**：懷疑過「韌體把活著的那顆貼錯字母」（例如失敗的那顆被跳過後，
索引往前補、把另一顆印成 `A`）——**逐行查過 `vl53l7cx_test.c` 所有跟感測器
身分有關的陣列存取（`pins[i]`／`s_dev[i]`／`s_results[i]`／`ok[i]`／
`s_seq[i]`），全部永遠用同一個迴圈變數 `i` 索引（`i=0`→A、`i=1`→B），
沒有任何地方會重新編號**。`ok[i]==false` 時 `vl53l7cx_test.c:372` 直接
`continue` 跳過那顆，`print_tof_line(pins[i].letter, ...)`（`vl53l7cx_test.c:429`）
用的 `pins[i].letter` 是編譯期常數，字母跟迴圈索引/初始化成敗完全無關，
**不可能印錯字母**。

**目前最合理的解釋**：兩次錄製的數字（seq、時長）不一樣，代表是**兩個不同
時段**，兩次之間某顆感測器的狀態變了——這正是**接線鬆動或銲點邊緣**的典型
症狀（這次通、reset 一次就不通）。**要確認的話，請做一次連續不中斷的錄製**
（reset → 開機 log → 緊接著的 `$T` 資料行都在同一個 session 裡），
才能同時看到「哪顆初始化失敗」跟「哪顆真的在送資料」，現在手上這兩段不能
互相對照。

### 為什麼 `drop_X=0` 不代表「那顆沒事」

`main/vl53l7cx_test.c:337` 開機時跑
`ok[i] = init_bus_and_sensor(i)`；**只要某顆的 `init_bus_and_sensor()`
回傳 `false`，主迴圈（`vl53l7cx_test.c:372`）就會對它永遠 `continue`**
——SENS 指令、data-ready 輪詢、drop 計數、`$T` 全部被跳過，
**永遠不會再重試**，不是暫時性的。`drop_*` 的計數邏輯就在這個被跳過的
區塊裡面，所以失敗那顆的 `drop_*` 會停在 0，**跟「一直讀取成功」長得
一模一樣，必須靠對應的 `$T,<A|B>` 有沒有行數來分辨，不能只看 `drop_*`**。

### 兩顆感測器是**兩條獨立 I2C 匯流排**，不是共用匯流排改位址

```c
static const sensor_pins_t pins[] = {
    { "Sensor A", 'A', GPIO_NUM_5, GPIO_NUM_4, I2C_NUM_0 },   // SCL, SDA
    { "Sensor B", 'B', GPIO_NUM_7, GPIO_NUM_6, I2C_NUM_1 },   // SCL, SDA
};
```
（`vl53l7cx_test.c:58-60`）——**A 用 `I2C_NUM_0`，B 用 `I2C_NUM_1`，
完全獨立的兩條線，兩顆都用同一個位址 `0x29`（`VL53L7CX_I2C_ADDR_7BIT`）**。
⚠️ **這代表「XSHUT 拉高拉低順序錯、兩顆撞同位址」這個常見失效模式在這個
硬體設計下完全不成立，可以直接排除**——沒有共用匯流排，`pins[]` 裡也沒有
XSHUT/LPn 這種 shutdown pin 欄位。**`vl53l7cx_platform.c:71` 的
`VL53L7CX_Reset_Sensor()` 註解直接寫明**「LPn 直接接 VCC，沒有 host GPIO
控制的重置線」——**兩顆的 LPn 都硬接電源，軟體完全碰不到，也不需要碰**。
哪顆沒資料，問題**只可能在那顆自己那條 I2C bus 或那顆模組本身**，跟另一顆
的線路無關。

⚠️ **有一條線索**：`vl53l7cx_test.c:55-57` 的註解——「實際接線跟 SDA/SCL 原本
規劃的 4,5/6,7 是反的，之前上機測試時發現的，用軟體對調而不是重新焊接」。
**這代表這塊板子的 GPIO4-7 這四支腳位過去確實發生過接線跟程式碼對不上的
情形**——現在的問題有沒有可能是同一類「哪支是 SDA、哪支是 SCL 兜錯」再犯，
或是接頭本身沒插到底、鬆動，值得優先懷疑。

### `status=1 alive=0` 是什麼意思

`vl53l7cx_platform.c:53/65`——`VL53L7CX_WrMulti`/`RdMulti` 只要底層
`i2c_master_transmit`/`i2c_master_transmit_receive`（2000ms timeout）沒回
`ESP_OK`，一律回傳 `1`，**不分 NACK、timeout、還是其他匯流排錯誤，全部塌成
同一個數字**。`vl53l7cx_is_alive()` 把幾次讀寫的 status 用 `|=` 疊起來，
只要任何一次失敗整個就非 0。**`status=1` 代表 I2C 交易本身沒完成**——
`device_id`/`revision_id` 根本沒讀到有效值，這裡的 `alive=0` 只是讀取失敗
的副產物，**不能解讀成「讀到晶片但 ID 不對」**（那種情況會是
`status=0, alive=0`，是不同的字）。搭配上面「沒有位址衝突可能」的結論，
`status=1` 幾乎可以肯定就是：**那條 I2C bus 上沒有裝置回應**——接線沒接好
或沒通電，**不是位址、不是軟體時序問題，而且軟體這邊沒有任何辦法補救**
（沒有重置線可以重打）。

### 韌體會不會「安靜地只跑另一顆」？——**會，而且現在看不出來是不是這樣**

`init_bus_and_sensor()` 失敗時**只在開機當下印一行 `ESP_LOGE`**（見下表），
之後**完全沒有任何持續性的提示**——不會反覆警告、`$STATUS` 沒有欄位講
「哪顆未初始化」、`SENS:<A|B>=1` 指令送下去也只會印
`SENS:<A|B>=1 (on)`（`uart_cmd.c:65`，**這行不檢查那顆到底有沒有初始化
成功，指令看起來「被接受了」但實際上從來沒有被套用到任何東西**，因為
`app_main` 主迴圈裡那塊已經被跳過，不會去讀這個指令）。

🔴 **這是一個需要修的缺口，但這次不動韌體**（板子是活的）：使用者現在唯一能
確認哪顆初始化成功的辦法，是**回頭找開機當下那幾行 log**，序列埠上
之後不會再出現任何相關訊息。

### 🔴 一分鐘檢查表

1. **回頭找開機時（`$STATUS` 出現前後那幾秒）的 log，找 `[Sensor A]`／
   `[Sensor B]` 開頭的行**——`idf.py monitor` 的 scrollback 往上滑，或用
   終端機的搜尋功能找 `is_alive failed`。哪一行出現，直接對應下面哪一段
   程式碼失敗：

   | 看到的字串 | 失敗在哪一步 | 意思 |
   |---|---|---|
   | `[Sensor <A\|B>] i2c_new_master_bus failed: ...` | 建立 I2C 匯流排本身就失敗 | GPIO 設定衝突或腳位被別的東西占用，**不像這次的情形**（另一顆用同一組 API 沒事） |
   | `[Sensor <A\|B>] i2c_master_bus_add_device failed: ...` | 掛上裝置失敗 | 同上，罕見 |
   | **`[Sensor <A\|B>] is_alive failed (status=%u alive=%u)`** | **I2C 匯流排建好了，但 ping 不到感測器晶片** | 🔴 **這次實測看到的就是這個**——代表那顆的 SDA/SCL 沒接對、沒接上，或模組沒通電。**先查這個** |
   | `[Sensor <A\|B>] vl53l7cx_init failed, status=%u` | ping 得到，但上韌體失敗 | I2C 通了但不穩定（雜訊、線太長、內部上拉電阻在 400kHz 下勉強），或模組本身壞了 |
   | `[Sensor <A\|B>] configuration failed` / `start_ranging failed` | 上韌體成功，設解析度/開始量測失敗 | 少見，通常代表前面其實已經半成功 |

   **一定要跟緊接著的 `$T,A`/`$T,B` 資料行一起看**（同一次連續錄製，不要
   拿不同時段的資料互相對照）——`print_tof_line()` 用的字母是編譯期常數，
   跟哪顆初始化成功綁死、不會印錯，所以「開機 log 說哪顆失敗」跟「$T 少了
   哪個字母」**必須一致**，不一致才需要再往下查。

2. **檢查板子上兩顆感測器各自的接線**：`GPIO5=SCL_A`、`GPIO4=SDA_A`、
   `GPIO7=SCL_B`、`GPIO6=SDA_B`（軟體已經照上面那條「SDA/SCL 對調」的
   註解接好，**不要自己再交換一次**，照這個對應查實際接線）。確認：
   - 失敗那顆的 SCL/SDA 兩條線真的接到模組對應腳，不是接錯或懸空
   - 失敗那顆的電源（VDD/GND）真的有接上、電壓正常——`is_alive` 失敗
     韌體端沒辦法分辨「線沒接」還是「沒通電」，這兩種都要排除
   - 接頭本身有沒有鬆動——**兩次錄製結果不一樣，優先懷疑這個**
     （見上方「目前最合理的解釋」）
   - 另一顆目前正常的那組接法，可以拿來對照「正確的接法長怎樣」

3. **兩條內部上拉電阻都是軟體開的（`enable_internal_pullup=true`），
   A/B 設定一樣**，不太可能是上拉電阻設定差異，優先懷疑接線本身而不是
   程式碼配置。

**這次沒有動 `vl53l7cx_test/main/` 底下任何東西，也沒有碰 `/dev/ttyUSB0`。**

### 1.2 真實 UART 的掉幀率 → 決定 `E05` 能不能開始錄

**誰在等**：`E05`（4 小時主資料集蒐集）的資料品質。

> **更正**：`B19` 一度回報「本機 pty 只用 18% 頻寬就掉 0.7%」。
> `B20` 實測推翻了它——**bridge 沒有掉幀**。18%→92% 頻寬、四個 SSE client
> 同時連著，掉幀率一律 **0.0000%**；裸 `readline()` 在 208% 標稱頻寬下也一幀不掉。
> 那 0.7% 是兩個主機端計數 bug，已修。`bridge_server.py` 一行都沒改。

**但 `B20` 只證明了「bridge 自己不掉幀」，證明不了真實 UART 不掉**：

| 限制 | 為什麼重要 |
|---|---|
| **pty 不是 UART** | 沒有電氣層、沒有真實 baud、沒有 FIFO overrun |
| **92% 那列是高幀率逼近的** | T04 收到 `REC:` 只印 log，**錄音 dump 期間的掉幀尚未被真實模擬** |
| **`$F` 沒參與** | 頻寬靠提高 `$T`/`$M` 幀率湊；真實是「更少但更長的行」，對讀取端更輕 —— 測法偏保守 |
| **每組只跑 10 秒** | 若真實掉幀率是 0.1%，10 秒內一幀都沒掉的機率約 3%。**不是上界為 0** |

- [ ] 跑 `tools/fw_regression.py`，看 `DropTracker.cross_check()` 的 `delta`
- [ ] **`delta > 0` 是傳輸層故障**（主機看到裝置不認為自己造成的損失），不是計數誤差
- [ ] **量測窗要夠長**：30 Hz 下需要**約 4.5 分鐘**連續擷取才有統計意義
      （`B03` 算過：短窗的二項分布標準差太大，10 秒的結果沒有意義）
- [ ] **真的錄一次音**，看 dump 期間 ToF 掉幀是否可歸因於頻寬（裝置沒送）
      而非 bridge（主機沒收）
- [ ] 🔴 **`E05` 開錄前先看一次 `quality` 事件的 `alarms`，空的才開始錄**

**🔴 量到非零掉幀率時，先看 `malformed` 計數，不要直接去查線材/baud/FIFO overrun**
（見 `reports/BOOT_OUTPUT.md` §2、§6）：

`uart_out_lock()` 只保護韌體自己寫的 `$` 行函式，`ESP_LOG*` 完全不走那把鎖，
而 `mic_task`/`uart_cmd_task` 是 priority 5、`app_main`（`$T` 的來源）預設
priority 1——高優先權隨時能在一行 `$T` 的 130+ 次 `printf()` 之間插隊。**這會
被主機端 `protocol.py` 正確拒絕（已驗證，見 `host/capture/test_protocol.py`
新增的 5 個測試），但那一行的 `seq` 會在 `DropTracker` 眼中造出一個缺口
——跟裝置真的沒送出那一幀，長得一模一樣。**

而且裝置自己的 `$H` `drop_*` 計數器不會把這算進去（那一幀確實被印出來了，
韌體不知道它被自己的 log 弄髒），所以 `cross_check()` 的 `delta` 會被推成正的、
`quality` 事件會跳出一則「傳輸途中遺失（UART overrun 或 bridge 跟不上）」的
紅色警示——**這句歸因在這個成因下是誤導的**，不是計數器本身錯，是提示文字
把使用者導去查錯的方向。

⚠️ **`ProtocolParser.stats.malformed`／`malformed_rate` 已經算出來了，但目前
沒有任何地方讀它**——`vl53l7cx_test/monitor/bridge_server.py` 沒有把它接進
`quality` 事件或 panel，純粹是個內部數字。在這條路徑被接上之前，**看到非零
掉幀率但摸不清是不是這個成因時，唯一能確認的辦法是自己讀 `ProtocolParser`
的 `stats.malformed_rate`**（`bridge_server.py` 目前沒有 HTTP endpoint 暴露它，
需要另外接一個除錯用的讀取點，或直接在 Python 互動環境裡查 `protocol_state["parser"].stats`）。

**量級（讀原始碼估的，不是實測，數字有誤差）**：穩態下唯一會週期性觸發這個
race 的來源是 `bone_mic.c` 的 `a15_perf` log（每 10 秒一次，`mic_task`，
priority 5）；`vl53l7cx_test.c` 自己也有一行同名 log，但那是**同一個 task**
印 `$T` 的，同 task 內是循序執行，不會撞到自己。其餘 `ESP_LOG*`（感測器 init
失敗、i2s 錯誤、`SENS`/`AMB`/`MEL`/`REC` 指令回應）都只在開機那一刻或使用者
發指令時才印，不是穩態背景噪音。

⚠️ **更正（下面這段先前寫錯了，數字差了一個量級以上）**：原本以為
`printf()` 印完就丟進 TX 緩衝區、幾乎瞬間返回，所以估成「千分之幾機率、
10 分鐘大概撞不到一次」。去查了 `uart_cmd.c:279` 實際呼叫的
`uart_driver_install(UART_NUM_0, 512, 0, 0, NULL, 0)`，**第三個參數
`tx_buffer_size` 是 0**——查 ESP-IDF 驅動原始碼確認 `tx_buffer_size == 0`
代表**沒有 TX ring buffer**，`printf()`/`uart_write_bytes()` 是照實際 wire
速度（460800 baud ≈ 46080 bytes/s）阻塞到送完為止，`uart_out_lock()`
持鎖的整段時間就是這行資料實際的傳輸時間，不是幾十微秒的 CPU 時間。

重新估：4×4 一行 `$T` ≈3.2ms 傳輸、8×8 一行 ≈12-14ms；`$T` 鎖持有時間占
整個幀週期的比例（占用率）4×4 @30Hz 約 **19%**、8×8 @10Hz 約 **25-28%**。
`a15_perf` 觸發時機跟這個週期無關，落在鎖持有窗口內的機率 ≈ 占用率本身

`a15_perf` 觸發約 60 次，預期撞上（弄丟一行 `$T`）約 **12-17 次**。

完整推導與**已驗證過的最小修法**（把這行 log 包進 `uart_out_lock()`，
兩行改動、`idf.py build` 過、0 warning、已改回去 `git diff` 乾淨）見

## 2. 未驗證的假設（錯了會讓分析結論反向）

### 2.1 zone 的物理佈局是不是 row-major？

**誰在等**：`D11`（逐 zone SNR）、`C05`/`C07`（熱力圖）、`D10`（crosstalk）。

ST 的 ULD 標頭**沒有文件化** zone 的物理佈局。目前全鏈路假設
`zone i → (i // 4, i % 4)`，程式與圖上都標了 `ASSUMED, unverified`。

**驗證方法（精確版，現在就做得成——已經兩顆都活著、環境幾乎全 `-1`，
是最乾淨的測試時機）**：

🔴 **不要只看面板熱力圖判斷「看起來對不對」**——面板的熱圖渲染本身就是
照同一個 row-major 假設畫的，**看熱圖會是循環論證：不管實際佈局對不對，
熱圖都會「看起來合理」，因為它跟你要驗證的假設用的是同一套映射**。
真正要看的是 `$T` **那一行的原始數字**，不經過面板轉譯。

1. **拿一隻手或一張紙，靠得很近**（10 公分以內，比背景反射的物體近很多——
   目前空景量到的有效值大約是 283mm/2308mm 那種距離，你要的效果是**明顯
   近很多、一看就知道是你的手造成的**，不是環境雜訊）。
2. **每次只挋住一個角落**，四個角落輪流做（不用一次做完，但做全部四個
   最乾淨——不只驗證對錯，連「轉了幾度、有沒有鏡像」都能一次確認）。
3. **看 `$T,A,...` 那一行第 6 個逗號之後的數字**（跳過
   `$T`,`A`,`seq`,`t_us`,`dim` 五個欄位，接下來 16 個是距離 `d0..d15`）
   ——**目前 4×4 模式（`dim=16`），照現在假設的 row-major，四個角落對應
   `d0`（左上）、`d3`（右上）、`d12`（左下）、`d15`（右下）**，
   但**你不用先信這個假設**：只要記下「這次遮的是哪個實體角落」，
   然後看**哪一個索引的值變了**，兩者對起來就知道實際的對應關係，
   對了就是驗證通過，不對就直接知道真正的映射長怎樣（順便修正
   `ASSUMED, unverified` 那個標記，不用再猜）。

⚠️ **方向跟直覺相反，這是最容易搞錯的地方**：**空景（沒東西在感測器前面）
是 `-1`（無效），不是 0。「遮住」那個角落不是讓它變無效，是讓那個角落
從 `-1` 變成一個有效的小數字**（因為原本那個方向探測不到東西、回波太弱
或超出範圍，你的手一放近，反而給了它一個有效目標）。**如果遮了之後那格
還是 `-1`，不是驗證失敗，是那個角落根本沒對到你放的位置**，換個角度/
更近一點再試。

⚠️ **錯了的話熱力圖會上下或左右翻轉**，而 `D11` 的產出是
「感測器該往哪個方向調」——**方向錯了，建議就是反的**。

「錯了會怎樣」的完整追查（會不會報錯／哪些數字看起來對但其實錯／
一分鐘判別法）見 `reports/ASSUMPTION_RISK.md` 「假設 1」。

（`AMB:1` 是另一個不同的測試——§5 `A16` 那條「遮住**一整顆**感測器看
